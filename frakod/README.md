# Fracode MCP — долговременная память для агентов

[Русский](README.md) | [English](README.en.md)

Это реализация внешнего long-term memory для LLM-агентов: архив разговоров и кода
лежит в сжатом виде, агент достаёт из него контекст по MCP, а не перекачивает
историю в промпт на каждом запросе.

## Откуда идея

Микро-модель (STS-Prog, ~11M параметров) обучалась сжатию последовательностей —
эксперимент в этом же репо, ветка `pc-carroll`. Модель предсказывала следующий
токен через синхронные драйвер-слои, и побочный продукт — компактная таблица
эмбеддингов токенов — использовалась как ключ поиска. Память выросла из модели,
которая учится сжимать.

## Что здесь честно, а что нет

Здесь два независимых механизма, и их важно не смешивать:

| | Архив (`codes.npy`) | Операционная память (`/remember`) |
|---|---|---|
| Что хранит | 24 Б/токен кодов + keys для реранка | сырой текст записи целиком |
| Запись | офлайн-сборка из корпуса | во время работы агента |
| Использует сжатие | да | **нет** |
| Файл | `frakod_index/*.npy` | `frakod_store.json` |

**«24 Б/токен» относится только к `codes.npy`.** Это само сжатие, и оно даёт
ADC-скрининг кандидатов. Но постоянный след архива на диске больше, потому что
для точного реранка читаются `keys_f16.npy` (384 Б/токен), а для лексического
слоя — `ids.npy` (4 Б/токен). Полный честный итог — `/index/accounting`:

```
N = 2 927 882 токена
codes.npy     =  67.0 МБ   24.0 Б/токен   ← это и есть «24 Б»
keys_f16.npy  = 1072.2 МБ  384.0 Б/токен  ← реранк кандидатов
ids.npy       =  11.2 МБ     4.0 Б/токен  ← лексический exact-слой
--------------------------------------------------------------
итого         = 1150.8 МБ  412.1 Б/токен
```

`keys_f16` можно держать не резидентно: реранк читает их `mmap`-ом с диска.

## Разделение вклада каналов (главное число)

Один архив, одни вопросы, разные каналы поиска — `test_24b_proof.py`
(после фикса лекс-слоя, окно `win=16`). Два архива: старый (BPE-512,
посимвольный) и **пересобранный на v7** (BPE-8192, d=256, S=16).

| канал поиска | старый архив | **архив v7** | медиана |
|---|---|---|---|
| ADC по кодам, запрос-вопрос | 0.00 | **0.30** | 638 мс |
| коды + реранк `keys_f16`, запрос-вопрос | 0.00 | **0.60** | 49 мс |
| лексический exact-слой | 1.00 | **1.00** | 17 мс |
| гибрид (`auto`) | 1.00 | **1.00** | 64 мс |
| ADC по кодам, запрос-сниппет | 0.00 | **0.00** | 648 мс |
| коды + реранк, запрос-сниппет | 0.00 | **0.17** | 53 мс |

**Что это значит честно.** Пересборка на согласованном токенизаторе **запустила
векторный канал**: с 0.00 до **0.60** (вопрос + реранк). Это подтверждает диагноз
— канал убивала не «дороговизна 24 байт», а рассогласование токенизатора,
эмбеддера и запроса. Но:

- **на сниппетах вектор почти не работает** (0.00–0.17) — при коротком запросе
  без шаблона усреднённое окно теряет иглу;
- **ADC в одиночку даёт 0.30** — 24-байтовое сжатие находит, но недостаточно
  точно; реранк по `keys_f16` поднимает до 0.60;
- **весь гибрид снова держит лекс-слой** (1.00).

Строгая оговорка к метрике: `recall@4` = «слово-игла встречается в тексте любого
из 4 вернувшихся окон». Строгий precision@4 лекс-слоя — **0.25** на вопросах,
**0.29** на сниппетах.

Важно про размер: `24 Б/токен` достижимо только при **d=192, S=12**. У архива v7
(d=256, S=16) код — `(N,2,16)` = **32 Б/токен**; keys при этом 512 Б/токен.
Компромисс «дешевле/точнее» нужно выбирать осознанно.

## 24 Б/токен: доказано на согласованном архиве

Схема работает, когда **токенизатор запроса совпадает с токенизатором архива** и
запрос строится тем же оператором, что и ключи. Проверка — `test_24b_code.py` и
`_qkey_check.py` на архиве `frakod_index_code10m` (10M токенов, корпус кода,
BPE-8192):

| метод запроса (истинная позиция известна) | top-1 | top-4 | cos |
|---|---|---|---|
| **контекстный запрос, окно RAD=4** (как в билдере) | 14/16 | 14/16 | **1.000** |
| монотокенный запрос `E[ids].mean(0)` (старый путь API) | 8/16 | 8/16 | 0.958 |

Сквозь живой API на том же архиве, 16 позиций из 10 млн, ADC по 24 байтам:

| канал | top-1 | top-4 | top-8 |
|---|---|---|---|
| ADC только по 24 Б | 0/16 | 3/16 | 7/16 |
| 24 Б + реранк по `keys_f16` | 0/16 | 3/16 | 7/16 |

Вывод: **24-байтовое сжатие несёт рабочую информацию** — 7 из 16 запросов
попадают в ±7 токенов, выбирая 16 кандидатов из 10 000 000 (в 625 000 раз
плотнее случайного). Ноль на архиве Hermes объясняется двумя конкретными
дефектами, а не физикой сжатия (см. ниже).

## Четыре корневые причины, найденные при аудите

1. **Архив Hermes построен посимвольным BPE-512.** В `meta.json` до фикса не
   было ни токенизатора, ни его типа; `ids.npy` содержит только значения 0…511,
   кириллица кодируется по одной букве (`фотосинтез` → 2 токена-обломка).
   Эмбеддер `sts_prog_seed0.pt` при этом (512, 192) — согласован с архивом, но
   семантики в посимвольном мешке нет.
   **Проверено и исправлено:** разделение разных русских текстов по cos —
   seed0 (512): 0.47…0.90 (среднее 0.70, почти коллинеарно) против v7 (8192):
   0.17…0.38 (среднее 0.30). Архив пересобран на v7 → вектор ожил (0.60).
2. **Асимметрия запрос/ключ в `frakod_api.py`.** Ключи архива — контекстное
   среднее с окном RAD=4, а запрос считался как `E[ids_q].mean(0)` без
   усреднения. На код-архиве это роняло cos с 1.000 до 0.958 и уводило top-1 на
   +4…5 токенов (8/16 вместо 14/16). **Исправлено:** запрос строится тем же
   скользящим средним, `RAD` берётся из `meta.json`.
3. **Два разных эмбеддера в одном процессе.** `recall` (архив) работал на
   `sts_prog_seed0.pt` (d=192, vocab=512), а `dvec` (`/resolve`, оперативная
   память) — на `ckpt_v7_night_50k.pt` (d=256, vocab=8192). **Частично
   исправлено:** `_sts_embed_table()` теперь выбирает чекпойнт по
   `meta.embed_ckpt`, а `dvec` по-прежнему на v7 — остаётся свести к одному.
4. **`embed_ckpt` писался как basename, а не путь.** Билдер клал в `meta.json`
   только имя файла, и если чекпойнт лежал не рядом с `frakod_api.py` (например
   `phase01/exp_vq/ckpt_v8_voc8k.pt`), API **молча откатывался** на
   `sts_prog_seed0.pt` — то есть ключи архива и запрос снова оказывались из
   разных таблиц, ровно как в причине №1. **Исправлено:** `meta.json` теперь
   несёт абсолютный путь (`embed_ckpt`) плюс имя (`embed_ckpt_name`); API
   разрешает оба варианта и, если нужного чекпойнта нет, **падает с внятной
   ошибкой**, а не подставляет другой эмбеддер. Добавлена сверка `d` эмбеддера
   с `D` архива. Проверено: v8-архив теперь грузит именно `ckpt_v8_voc8k.pt`
   (8192, 192).

## Бенч против RAG и Mem0

Срез истории Hermes, 30 вопросов с иглами (реально использовано 25 — столько
дал генератор после дедупликации), одна чат-нода. Файл — `bench_results.json`,
воспроизведение — `bench_memory_systems.py`.

| | recall@4 | токенов в промпте | поиск | LLM-токенов на запись | хранилище |
|---|---|---|---|---|---|
| без памяти | 0.00 | 151 | — | 0 | — |
| RAG (chroma) | 0.24 | 263 | 27 мс | 0 | 20.3 МБ |
| Mem0 | 0.08 | 684 | 63 мс | 1 686 418 | — |
| **Fracode** | **1.00** | 560 | 17 мс | **0** | **1150.8 МБ** |

Честные оговорки к таблице:

- **Запросы не эквивалентны.** RAG и Mem0 получают короткий вопрос. Fracode в
  исходном бенче получал 160-символьный фрагмент, содержащий искомое слово
  дословно, — а игла по построению встречается в корпусе один раз. Теперь бенч
  считает оба протокола (`query` и `snippet`); в таблице выше — `query`, т.е.
  равные условия. На `snippet` Fracode тоже 1.00.
- **Fracode берёт числом за счёт лексического exact-слоя, а не вектора.** Это
  точный поиск слов по `ids.npy`, то есть по сути инвертированный индекс. Такой
  результат ожидаем для задачи «редкое слово встречается в корпусе один раз» и
  не означает превосходства векторного сжатия. Строгий precision@4 — 0.25.
- **Задача Mem0 другая.** Mem0 не ищет по корпусу, а извлекает структурированные
  факты через LLM — отсюда 1.68M токенов записи (это ~105% размера корпуса).
  Сравнивать 0.08 и 1.00 как две реализации одной задачи некорректно; Mem0 честно
  показывает цену LLM-инжеста.
- **Хранилище Fracode теперь считается полностью** (коды + keys + ids), а не
  только по кодам, как раньше.

## Как устроено

1. **Архив** — BPE-токенизированный текст, разбитый на окна; каждое окно
   кодируется product-quantizer'ом на эмбеддингах микро-модели.
   `frakod_index_build.py`.
2. **Поиск** — ADC-скрининг кандидатов по 24-б кодам, реранк по `keys_f16`,
   плюс лексический exact-слой (редкие слова запроса ищутся точными
   последовательностями токенов по `ids.npy`, IDF-ранжирование).
   Гибрид (`/recall`, режим `auto`). `frakod_api.py`.
3. **MCP** — stdio-сервер `frakod_mcp.py`, 8 инструментов: `remember`, `link`,
   `resolve`, `chain`, `recall`, `recall_vector_only`, `ask_llm`, `index_stats`.
   Адреса — `frk1:<slot>.<id>`, `link`/`chain` принимают и адрес, и голый id.
   ```json
   {"mcpServers": {"frakod": {"command": "python", "args": ["frakod_mcp.py"]}}}
   ```
4. **Переносимость истории** — `ingest_chat.py` импортирует выгрузки диалогов из
   других агентов (форматы `a`/`b`/jsonl/txt) в тот же архив.

## Быстрый старт

```bash
pip install -r requirements.txt
# 1) построить архив из своего текста
FRK_CORPUS=my_history.txt FRK_OUTD=frakod_index python frakod_index_build.py
# 2) поднять API (порт 8781)
python -m uvicorn frakod_api:app --port 8781
# 3) подключить MCP-клиент к frakod_mcp.py
```

Для векторного канала нужен чекпойнт `sts_prog_seed0.pt`; для лексического —
корпус (тот же, что кодировали); путь задаётся `FRK_CORPUS`, иначе ищется рядом
с пакетом.

## Что делать дальше

1. **Свести два эмбеддера к одному.** `recall` уже берёт чекпойнт из
   `meta.embed_ckpt`, но `dvec` (`/resolve`) всё ещё жёстко на v7. Пока они
   разные, `/resolve` и `/recall` живут в разных векторных пространствах.
2. **Поднять сниппет-режим.** Вектор даёт 0.60 на полном вопросе и 0.00–0.17 на
   сниппете. Причина — контекстное усреднение размывает короткий запрос. Вариант:
   строить запрос как среднее по нескольким якорным окнам или перейти на
   многоуровневый ключ (не один усреднённый вектор на позицию).
3. **Дообучить эмбеддер под d=192 с БОЛЬШИМ словарём — ночью. Пайплайн готов.**
   Пара (d=192, vocab=8192) **уже реализована**: `phase01/exp_vq/train_v8_uplift.py`
   строит смешанный корпус (код + реальная история), обучает PurePCLM d=192 l=8
   и сохраняет `ckpt_v8_voc8k.pt` + `tok_v8.json`. Это ровно 24 Б/токен кодов.
   Геометрия у неё **лучше**, чем у v7: cos между разными русскими текстами
   min=−0.13 / max=0.23 / mean=0.04 против 0.17…0.38 / mean=0.30 у v7 —
   эмбеддер различает тексты, а не тянет всё в одну точку. **Но чекпойнт на
   диске — smoke-прогон** (ppl 6492–8254; у v7 ~40–100), поэтому архив на этой
   паре векторный канал не оживляет даже с правильным эмбеддером:
   adc24 0.00, vec+rerank 0.00, лекс 0.90.

   Чекпойнт грузится в `PurePCLM(d=192, l=8)` **без missing/unexpected** —
   архитектура верна, не хватает только обучения. Запуск одной командой:

   ```bash
   python night_v8_pipeline.py --steps 10000     # ~3 ч; 8000 → ~2.4 ч
   ```

   Пайплайн сам: бэкапит чекпойнт, обучает, замеряет ppl до/после, пересобирает
   архив, поднимает API, гоняет `test_24b_proof.py` и `test_24b_code.py`, кладёт
   `night_v8_report.json` и проверяет, что `b_per_tok_codes == 24.0`. Проверен
   в режиме `--skip-train` — вся цепочка проходит. **Это единственный известный
   путь получить 24 Б/токен и семантику одновременно.**

   Ориентир по ppl (v7 за первые 500 шагов упал до 454, к 60k — до 40):
   нужно ≥8000 шагов, чтобы вектор имел шанс ожить.
4. **Снять зависимость от `keys_f16`.** ADC даёт 0.30 против 0.60 с реранком —
   разрыв ещё велик, но его можно сократить лучшим обучением кодобуков, и тогда
   постоянный след падает с 548 до ~36 Б/токен.
5. **Заменить линейный скан.** `_recall_cpu` идёт по всем N токенам (~640 мс).
   Нужен ANN/HNSW по кодовым префиксам.
6. **Определить модель распространения.** Сейчас GPL-3.0. Решить до внешних PR.

## Почему круто (что остаётся правдой)

- **Запись бесплатна**: ни одного LLM-вызова на инжест архива.
- **Гибрид даёт recall@4 1.00** при медиане ~64 мс на 2.4M токенов.
- **24-байтовое сжатие проверено и оживлено**: на согласованном архиве (v7,
  vocab=8192) ADC в одиночку — 0.30, с реранком — 0.60; на код-архиве через
  живой API top-8 7/16 из 10 млн. Схема работает, когда устранены четыре
  интеграционные проблемы.
- **Пара (d=192, vocab=8192) существует и валидна** — её геометрия лучше, чем
  у v7; не хватает только обучения. Именно она даёт 24 Б/токен и семантику
  разом, и её ночной пайплайн готов к запуску.
- **Всё локальное**, лицензия GPL-3.0, ~1.5k строк python.
