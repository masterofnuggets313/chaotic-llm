# Fracode MCP — переносимая долговременная память для агентов

[Русский](README.md) | [English](README.en.md)

Внешняя долговременная память для LLM-агентов. Архив разговоров и кода лежит
на диске в сжатом виде, агент достаёт из него нужный контекст по MCP — вместо
того чтобы перекачивать всю историю в промпт на каждом запросе.

**Главное отличие от RAG и KV-кэша:** память — это отдельный файл, который
можно передать другому агенту. Модель A записала, модель B прочитала.
Ничего не пересобирается из сырого текста на стороне B.

```
A:  memory_export_selfcontained(path="mem.frk1x")   → 48.7 МБ, 3.5 с
    (передать файл любым способом)
B:  memory_import_selfcontained(path="mem.frk1x.npz", name="b_archive")
    memory_verify(path="b_archive")                 → recall@8 = 0.875
```

Проверено на чистой машине: в каталоге агента B лежали **только** эти файлы и
два python-файла. Ни одного файла машины A, ни одного чекпойнта проекта.

## Откуда идея

Микро-модель (STS-Prog, ~11M параметров) обучалась сжатию последовательностей —
эксперимент в этом же репо, ветка `pc-carroll`. Модель предсказывала следующий
токен через синхронные драйвер-слои, и побочный продукт — компактная таблица
эмбеддингов токенов — стал ключом поиска. Память выросла из модели, которая
учится сжимать.

## Сколько занимает память

Два независимых механизма, их важно не смешивать:

| | Архив (`codes.npy`) | Оперативная память (`/remember`) |
|---|---|---|
| Что хранит | 24 Б/токен кодов | текст записи целиком |
| Запись | офлайн-сборка из корпуса | во время работы агента |
| Сжимает | да | нет |
| Файл | `frakod_index/*.npy` | `frakod_store.json` |

**«24 Б/токен» относится к `codes.npy`** — это само сжатие, и на нём работает
ADC-скрининг кандидатов. Полный след архива на диске больше: для точного
реранка исторически читались `keys_f16.npy`, для лексического слоя — `ids.npy`.

Актуальный архив (v8, N = 2 189 372 токена):

```
codes.npy      =   50.1 МБ    24.0 Б/токен   ← это и есть «24 Б»
keys_f16.npy   =  801.8 МБ   384.0 Б/токен   ← реранк; НЕ НУЖЕН (см. ниже)
ids.npy        =    8.4 МБ     4.0 Б/токен   ← лексический exact-слой
cbook (L0+L1)  =    0.4 МБ
-------------------------------------------------------------
ядро памяти (коды + кодобуки + ids + meta) = 58.8 МБ = 28.2 Б/токен
полный след                                = 860.6 МБ = 412.2 Б/токен
```

**`keys_f16` я не использую.** Он в пространстве конкретного энкодера и
весит в 16 раз больше самих кодов. Реранк по сырым ключам измеренно **вредит**:
ADC-only 0.900 против rerank 0.820 (`recall@8`, v8-архив). В переносимый пакет
он не входит вообще.

Размер кода: `24 Б/токен` — это **d=192, S=12, K=256, L=2**. Другие конфигурации
дают другой код: при d=256, S=16 код — `(N,2,16)` = 32 Б/токен.

## Как быстро и точно ищет

### 24 Б/токен на реальном архиве (v8, 2 189 372 токена)

Ключ полного ранга, ADC-скрининг, метрика — `recall@8` с допуском 4 токена
(ключи = context-avg окном RAD=4, поэтому точечная позиция физически размыта).
Сид 7, nq=64.

| N | recall@8 (24 Б/ключ) | потолок различимости |
|---|---|---|
| 4 096 | **1.000** | 0.938 |
| 8 192 | **1.000** | 0.812 |
| 16 384 | **1.000** | 0.938 |
| 32 768 | **0.984** | 0.875 |
| 65 536 | **0.984** | 0.781 |
| 131 072 | **0.969** | 0.656 |
| 262 144 | **0.969** | 0.688 |
| 524 288 | **0.969** | 0.797 |

*Прежние числа этого ряда (0.828 → 0.234 на 4k → 64k) получены на **вырожденном
ключе** (`external_keys` использовала только 16 из 192 координат из-за
`col = idx % sub`). Баг исправлен 11.09, проверено в `evidence/D1_CLOSED_2026-09-11.md`.
На исправленном ключе деградации почти нет.*

### Что именно измеряет `recall@8`

Диагностика (30 проб): ближайший кандидат совпадает с истиной в **0.83** случаев,
при этом в среднем **3 из 8** кандидатов лежат в пределах 4 токенов. То есть
вектор находит **окно** вокруг истины, а не точный токен — прямое следствие
`context-avg` ключей. Контроль на перемешанных кодах даёт **ровно 0.00** по всем
радиусам: кодобук действительно адресует, а не «любой запрос попадает в топ-8».

## Энкодер — главное узкое место, и он же — решение

Я обязан сказать это прямо, потому что это измерено, а не предположено.

Архив выше построен на **внутренней** таблице эмбеддингов микро-модели. У неё
есть фундаментальный дефект: **косинус между эмбеддингами двух разных текстов
равен нулю** (mean −0.000, max|·| 0.256). То есть содержание в представлении
отсутствует, а адрес держится только на позиционном слагаемом. Проверено
четырьмя независимыми тестами (`addr_diag.py`, `path_b_addr_signal.py`).

Замена энкодера меняет всё. Один и тот же честный протокол
(207 вопросов, корпус диалога, золото = все перекрывающие чанки, bootstrap 1000,
seed 20260912):

| энкодер | бюджет | recall@4 | 95% CI |
|---|---|---|---|
| наша модель `v8_dialog_seed0.pt` | 4096 Б/век | **0.087** | [0.053, 0.126] |
| `bge-m3`, сырой | 4096 Б/век | **0.517** | [0.449, 0.585] |
| `bge-m3` + сжатие 20 Б/окно | 20 Б | **0.319** | [0.261, 0.382] |
| потолок (запрос = свой чанк) | — | 1.000 | — |

Читается так:

* **Смена энкодера — ×6** (0.087 → 0.517). Это не тонкая настройка, это разница
  между «не работает» и «работает».
* **Сжатие в 205× стоит 1.6×** (0.517 → 0.319). Цена, а не обрыв: канал выживает.
* Контроли (SHUFFLED, RANDOM, потолок с запретом золота) дают 0.000 →
  измеритель проверен, числам можно верить.

### Как включить внешний энкодер

```bash
FRK_ENCODER=ollama FRK_EMBED_MODEL=bge-m3 \
FRK_TOK=tok_v8_dialog.json FRK_NO_KEYS=1 \
python frakod_index_build.py 10000000
```

Что при этом меняется (и почему это не «костыль», а честная модель):

| | внутренний архив | внешний архив |
|---|---|---|
| единица адреса | токен | **окно** (по умолчанию 800 симв., перекрытие 160) |
| ключ | context-avg таблицы токенов | вектор окна от энкодера |
| `key_context_rad` | 4 | **0** (перекрытие окон уже даёт контекст) |
| S (подвекторов) | 12 при d=192 | **подбирается под d** (d=1024 → 8) |
| цена | 24 Б/токен | **20 Б/окно** (16 кодов + 4 лекс) |
| читается без энкодера | да | **нет** — энкодер это зависимость |

**Архив НЕ хранит таблицу эмбеддингов корпуса.** Соблазн положить её рядом
велик (и я его проверил): это дало бы 4 КБ/окно вместо 20 Б и, хуже того,
превратило бы архив в утечку — готовые ответы на собственные запросы внутри
файла. Внешний энкодер — зависимость архива, как libc для бинарника.

### Реестр энкодеров и проверка согласованности

Раз энкодер — зависимость, читатель обязан знать, **где его взять**, и уметь
**проверить, что взял тот**. Оба механизма встроены:

1. **`meta.json` → `encoder_kb`** — реестр: модель, бэкенд, команда установки,
   URL, размерность. Достаточно, чтобы поднять нужный энкодер на чистой машине:

   ```json
   "encoder_kb": {
     "model": "bge-m3", "backend": "ollama",
     "how": "ollama pull bge-m3",
     "api": "http://localhost:11434/api/embed",
     "d": 1024, "normalize": true, "unit": "window"
   }
   ```

2. **Контрольные окна `meta.json` → `enc_probe`** — при сборке сохраняются 5
   окон корпуса и их векторы (≈25 КБ). Перед чтением Fraкod кодирует эти же
   окна энкодером читателя и **ищет их в архиве**: если находит нужное окно —
   канал живой.

   **Критерий — ЧИТАЕМОСТЬ, а не «тот же ли вектор».** Это исправлено 12.09:
   раньше принималось `cos ≥ 0.999`, и критерий давал **ложный отказ**.
   Измерено: `snowflake-arctic-embed2` имеет `min cos = 0.435` к архиву bge-m3
   (порог 0.999 его отверг бы), но при этом **читает архив с `recall@4 = 0.227`
   против потолка 0.319** — 71% канала живы. Правильный вопрос: «находит ли он
   нужное окно», а не «совпадает ли вектор».

   | энкодер читателя | probe_recall@4 | min cos | вердикт |
   |---|---|---|---|
   | bge-m3 (свой) | **1.0** | 1.000 | читает |
   | snowflake-arctic-embed2 | **0.8** | 0.435 | **читает** (старый порог врал) |
   | nomic-embed-text (d=768) | — | — | отказ: другая размерность, нужен адаптер |

   Порог: `probe_recall@4 ≥ 0.6` (3 из 5 окон). `cos` остаётся в ответе как
   диагностика, но **вердикт по нему не ставится**.

   Если энкодер не тот, `recall` и `memory_verify` возвращают **явный отказ**
   с причиной, а не тихий нулевой recall:

   ```json
   {"ok": false,
    "error": "энкодер вернул d=768, а архив требует d=1024: прямой поиск невозможен. Нужен АДАПТЕР …",
    "hint": "Возьмите энкодер той же размерности (см. meta.encoder_kb) или обучите адаптер."}
   ```

Это и есть «энкодер едет вместе с памятью» не как лозунг, а как протокол:
память + спецификация того, чем её читать + проверка, что спецификация соблюдена.

## Перенос памяти между агентами

Формат `.frk1x` (npz). Что едет:

| Компонент | Б/токен | Зачем |
|---|---|---|
| `codes.npy` | 24.0 | адреса узлов — архитектурно нейтральны |
| `cbook_l0/l1.npy` | — | без них коды = шум |
| `ids.npy` | 4.0 | лексический слой |
| `encoder_w.npy` | — | **энкодер A**: без него B не построит запрос. **Только для внутреннего энкодера** |
| `enc_probe.npy` | — | **контрольные окна**: B проверяет, тем ли энкодером читает |
| `tokenizer.json` | — | **токенизатор A**: иначе позиции разъедутся с текстом |
| `meta.json` + `store.json` | — | описание архива + текстовые записи и рёбра |

Размер зависит от архива. На архиве 10M-класса (31 595 окон, корпус 20.2M симв)
пакет — **2.1 МБ**; на v8-архиве с внутренним энкодером — 48.7 МБ (там в пакет
входит таблица эмбеддингов).

**Для внешнего энкодера (bge-m3 через Ollama) `encoder_w.npy` в пакет НЕ идёт** —
его в архиве нет по построению, запрос строится через Ollama. Пакет честно
пишет в манифесте: «B обязан поднять тот же энкодер». Раньше в такой пакет
вкладывалась чужая таблица `sts_prog_seed0.pt` (512×192) при d=1024 у архива,
и пакет ложно называл себя самодостаточным — исправлено 13.09.

### Сквозная проверка переноса

`_test_transfer.py` прогоняет полный круг: экспорт → импорт в новый каталог →
**второй API** (эмуляция машины Б) → те же запросы. Результат
(`evidence/transfer_roundtrip.json`):

| | |
|---|---|
| позиции совпали с агентом А | **20/20** |
| текст совпал | **20/20** |
| перекрёстная проверка `memory_verify` | `recall = 1.0`, расхождение позиций **0.0** |
| контроль энкодера у B | `ok=true`, `min cos = 1.0` |

MCP-слой проверяется отдельно, настоящим stdio-запуском сервера
(`_test_mcp_stdio.py`, `evidence/mcp_stdio_test.json`): 14 инструментов, ответы
`ok=true`, при мёртвом API инструмент возвращает `ok=false` и **не роняет
сервер**.

### Отрицательный результат, который стоит знать

Я проверял гипотезу, что память прочитается **чужим** энкодером. Она
**опровергнута**: 15 кандидатов, `recall@8 = 0.000` у всех, медиана промаха
87–172 тысячи токенов. Причина: кодобук — производное от энкодера, 256
центроидов описывают конкретное пространство.

Поэтому честная формулировка такая:

> **Модели разные — память общая. Но энкодер едет вместе с памятью.**

Это слабее, чем «чистый артефакт читается кем угодно», зато измерено.
Артефакт: `evidence/cross_encoder_NEGATIVE_2026-09-11.md`.

## Архитектура

1. **Архив** — BPE-токенизированный текст, разбитый на окна; каждое окно
   кодируется product-quantizer'ом на эмбеддингах микро-модели.
   `frakod_index_build.py`.
2. **Поиск** — ADC-скрининг по 24-б кодам, плюс лексический exact-слой
   (редкие слова запроса ищутся точными последовательностями токенов по
   `ids.npy`, IDF-ранжирование). Гибрид — `/recall`, режим `auto`.
   `frakod_api.py`.
3. **MCP** — stdio-сервер `frakod_mcp.py`, 14 инструментов. Адреса —
   `frk1:<slot>.<id>`, `link`/`chain` принимают и адрес, и голый id.

| Инструмент | Что делает |
|---|---|
| `remember` / `link` / `resolve` / `chain` | текстовая память + граф рёбер |
| `recall` / `recall_vector_only` | поиск по архиву (гибрид / чистое 24 Б) |
| `index_stats` | бухгалтерия архива побайтово |
| `ask_llm` | вопрос LLM с контекстом из памяти |
| `memory_manifest` | что переносимо, что нет, и почему |
| `memory_export` / `memory_import` | перенос без энкодера (`frk1x/1`) |
| **`memory_export_selfcontained`** | **перенос с энкодером (`frk1x/2`)** |
| **`memory_import_selfcontained`** | **развернуть автономный архив** |
| `memory_verify` | **независимая проверка переноса** |

```json
{"mcpServers": {"fracode": {
  "command": "python",
  "args": ["frakod_mcp.py"],
  "env": {"FRK_API": "http://127.0.0.1:8781"}
}}}
```

## Быстрый старт

```bash
pip install -r requirements.txt

# 1) построить архив на ВНЕШНЕМ энкодере (рекомендуемый путь — см. «Энкодер —
#    главное узкое место»): 20 Б/окно, качество поиска на порядок выше своего v8
FRK_ENCODER=ollama FRK_EMBED_MODEL=bge-m3 FRK_TOK=tok_v8_dialog.json \
FRK_NO_KEYS=1 FRK_CORPUS=my_history.txt FRK_OUTD=frakod_index \
  python frakod_index_build.py

# 2) поднять API. Прямой запуск работает (точка входа добавлена 12.09):
FRK_IDXD=frakod_index FRK_PORT=8781 python frakod_api.py
#   эквивалентно: python -m uvicorn frakod_api:app --port 8781

# 3) подключить MCP-клиент к frakod_mcp.py
```

Требуется Ollama с моделью `ollama pull bge-m3` на `localhost:11434`.
Если в `FRK_IDXD` нет `codes.npy`, запуск падает с явным сообщением, а не
молча. До 12.09 `python frakod_api.py` молча завершался с пустым логом — точки
входа просто не было; теперь она есть.

Для векторного канала нужен чекпойнт эмбеддера; для лексического — корпус
(тот же, что кодировали). Путь задаётся `FRK_CORPUS`, иначе ищется рядом с
пакетом. Каталог архива можно задать через `FRK_IDXD`; без него берётся
`frakod_index`, а если его нет — последний `frakod_index_v*` по времени сборки.

**Измеренная задержка** (207 вопросов, живой HTTP, `evidence/latency_N*.json`):
полный круг **90.7 мс** на 7 934 окнах и **104.5 мс** на 31 595; из них **на сам
поиск приходится 1.1 и 3.0 мс** соответственно, остальное — время внешнего энкодера.

**Сколько текста отдаёт `/recall`.** Для оконного архива вокруг найденной
позиции берётся ±`FRK_WIN_CTX` окна (по умолчанию 1, то есть 1920 символов,
обрезка — `FRK_TXT_CAP`, по умолчанию 2000). Это не косметика: при обрезке до
600 символов факт оказывался в выдаче в 44% случаев, при ±1 окне — в **59%**
(`evidence/bench_fact_ctx*.json`, прирост +0.140, p = 3.7e-9, парный тест).

**Две версии метрики «нашёлся ли факт» — цитируйте строгую.**

| | k=4 | k=8 |
|---|---|---|
| `snippet_hit` — мягкая, хватит 40 символов подряд | 0.4783 | 0.5894 |
| **`snippet_full` — строгая, весь фрагмент целиком** | **0.3913** | **0.5121** |

Мягкая завышает на 0.077. Проверка: на синтетическом демо-корпусе она даёт
**ровно 1.0000** при recall 0.21 (40 символов шаблонной фразы находятся где
угодно), а строгая там даёт 0.208 = recall. Метрику, которая на любой ответ
кричит «нашлось», нельзя показывать в одиночку.

## Проверка из коробки (без ваших данных)

Все числа в этом README получены на корпусах, которые нельзя опубликовать.
Поэтому в репозитории лежит синтетический демо-корпус и готовый бенч к нему —
за пять минут вы получаете работающий архив и **свои** числа:

```bash
# 1) демо-корпус (1.2 МБ) и вопросы к нему
python make_demo_corpus.py --out demo_corpus.txt --n 2000
python make_bench.py --corpus demo_corpus.txt --out demo_bench.json --n 120
#   без генеративной модели: добавьте --no-llm (запросы из редких терминов)

# 2) собрать архив и поднять API
FRK_ENCODER=ollama FRK_EMBED_MODEL=bge-m3 FRK_TOK=tok_v8_dialog.json \
FRK_NO_KEYS=1 FRK_CORPUS=demo_corpus.txt FRK_OUTD=frakod_index_demo \
  python frakod_index_build.py
FRK_IDXD=frakod_index_demo FRK_PORT=8781 python frakod_api.py

# 3) замерить
FRK_BENCH=demo_bench.json python _bench_fact.py
```

## Что где лежит

```
frakod_api.py  frakod_mcp.py  frakod_index_build.py   продукт: API, MCP, сборка архива
make_bench.py  make_demo_corpus.py                    бенч на любом корпусе + демо-данные
_bench_fact.py  _test_mcp_stdio.py  _test_transfer.py  тесты и бенчи (запускаются)
_diag_fact_paired.py  _bench_latency.py               статистика и замер задержки
evidence/                                             файл-источник каждого числа из README
docs/                                                 роадмап, аудит, протокол переноса
models_pc.py  train_extmem.py  frk1x.py               модель и обучение (научный трек)
```

**Почему файлы называются `frakod_*`, а продукт — Fracode MCP.** Внутренняя
инфраструктура (имена файлов, переменные `FRK_*`, формат пакета `frk1x`)
складывалась исторически, и переименование ломает ночные пайплайны и тесты.
Наружу продукт называется только Fracode: так он отдаётся в MCP
(`serverInfo.name = fracode`) и так он написан в документации.

## Что честно НЕ показано

Список короткий, но принципиальный:

- **Модель, обученная с Fracode-памятью, против KV-трансформера при равной
  памяти** — не показано.
- **Скорость.** Fracode **медленнее** KV-кэша: 1.63× с быстрым ADC (ценой +2.2% PPL)
  и до 5.2× на точном пути. Заявлять ускорение нельзя ни в каком виде — только
  обмен «память за скорость».
- **10 млн токенов** — обещание «~280 МБ» получено экстраполяцией
  (24 Б × 10M), реальный архив такого размера не собран.
- **`recall@8` ≠ «нашлась нужная мысль»** — это восстановление позиции
  с допуском. Продуктовый бенчмарк не поставлен.
- **Чужим энкодером память не читается** — измеренный отрицательный результат,
  см. выше.
- **Транспорт** — файл вручную. Нет object-storage, хэш-адресации,
  инкрементальных дельт.

## Почему это круто (без преувеличений)

- **Запись бесплатна**: ноль LLM-вызовов на инжест — в отличие от схем, где
  каждый факт прогоняется через модель.
- **Автономный архив в 17.7 раза меньше полного следа**: 48.7 МБ против
  860.6 МБ, при этом `keys_f16` (802 МБ) выброшен без потери качества.
- **Память — это файл.** Её можно передать, скопировать, положить в хранилище.
  Она не живёт внутри модели и не пересобирается из текста на новом хосте.
- **Работает как обычный MCP-сервер** — подключается к любому агенту.
- **Всё локальное**, GPL-3.0, чистый python. Никаких внешних API.
