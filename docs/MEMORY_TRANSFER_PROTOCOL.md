# Протокол переноса памяти `frk1x`

**Статус:** реализовано и проверено 11.09.2026, 19:24–19:53 UTC.
**Файлы:** `frakod_api.py` (эндпоинты), `frakod_mcp.py` (инструменты),
`frk1x.py` (упаковка и `exp_cross_encoder.py`).
**Все числа ниже — из живых прогонов, не из манифеста.**

> **ГЛАВНОЕ, что изменилось после измерения.** Я проверил гипотезу «память
> читается чужим энкодером» — она **опровергнута**: recall@8 = 0.000 у всех
> 15 проверенных кандидатов. Поэтому «переносимая память» — это **память
> вместе с её энкодером**, а не «чистый артефакт». Формат `frk1x/2` возит
> энкодер и токенизатор внутри себя. Детали — раздел 5.

## 0. Зачем это вообще

Компрессия — не уникальность. Сжать контекст умеют все: у Google есть RAG, у
Anthropic «contextual retrieval», у DeepSeek свой MLA. Уникально **другое**:

> Память — самодостаточный артефакт, который не является частью весов модели.
> Модель A её записала. Модель B её прочитала. Модели разные, память одна.

Всё остальное (RAG, KV-кэш, long-context) так не умеет by design: там память
либо живёт в активациях конкретной модели (KV), либо пересобирается заново из
сырого текста на каждом хосте (RAG). Перенос в чужую архитектуру без
пересборки — это то, чего в продакшне пока ни у кого нет.

**Уточнение, которое стоит мне честности:** «модели разные» верно, «энкодер
разные» — **нет**. Энкодер едет с памятью. См. раздел 5.

Файл `.frk1x` — физическая упаковка этой идеи.

## 1. Что именно переносится

| Компонент | Размер (v8, 2.19M токенов) | Б/токен | Переносимость |
|---|---|---|---|
| `codes.npy` | 50.1 МБ | 24.0 | **межархитектурная** — это индексы, не веса |
| `cbook_l0/l1.npy` | 0.4 МБ | — | **обязательно** — без них коды = шум |
| `ids.npy` | 8.4 МБ | 4.0 | переносится |
| `encoder_w.npy` | 6.0 МБ (3 МБ в float16 внутри пакета) | — | **обязательно** (см. §5) |
| `tokenizer.json` | 0.5 МБ | — | **обязательно** (см. §6) |
| `meta.json` + `store.json` | 2 КБ | — | описывают архив и хранят текст |
| **итого самодостаточный архив** | **~66 МБ** | — | |
| **итого пакет `.frk1x` (сжатый)** | **48.7 МБ** | — | |
| `keys_f16.npy` | 801.8 МБ | 384.0 | **не нужен вообще** |

Ядро памяти: **58.8 МБ = 28.2 Б/токен** против полного следа 860.6 МБ — в
**14.6 раза** меньше. Энкодер и токенизатор добавляют 6.5 МБ: цена
самодостаточности ничтожна по сравнению с выброшенными 802 МБ.

От `keys_f16` отказываемся сознательно — реранк по сырым ключам измеренно
вредит (ADC-only 0.900 против rerank 0.820, `recall@8`, v8-архив).

### Почему `codes.npy` переносим, а `keys_f16` — нет

`codes.npy` — это **индексы в кодобуке**. Кодобук обучен детерминированно на
корпусе, сами коды — просто числа 0..255. В них нет ни одного параметра чьей-то
модели. Поэтому артефакт не знает, кто его записал.

`keys_f16.npy` — это сырые 192-мерные векторы в пространстве конкретного
энкодера. Другая модель живёт в другом пространстве, и раскладывать эти
векторы ей нечем. При этом `keys_f16` **воспроизводим** из `codes` + `cbook` +
`encoder_w` — поэтому его и не надо возить.

## 2. Формат `.frk1x`

```
.frk1x  =  .npz (numpy zip)

frk1x/2 (рекомендуемый, самодостаточный):
  codes          uint8   (N, 2, S)      — адреса узлов
  cbook_l0       float32 (S, K, sub)    — кодобук уровня 0
  cbook_l1       float32 (S, K, sub)    — кодобук уровня 1
  ids            int32   (N,)           — лекс-слой
  encoder_w      float16 (V, d)         — ЭНКОДЕР A (таблица эмбеддингов)
  _tokenizer_json uint8                 — файл tokenizers.Tokenizer
  _manifest_json uint8                  — манифест пакета
  _meta_json     uint8                  — meta.json
  _store_json    uint8  (опц.)          — store.json
  keys_f16       float16 (N, D)         — опционально, только для L-same

frk1x/1 (устаревший): то же, но без encoder_w и токенизатора.
```

**Почему npz, а не zip/pickle:**

- `np.savez` не требует pickle: `allow_pickle=False` при чтении работает.
  Я специально убрал словари `meta`/`store` из прямых полей: `savez` на голом
  dict сделал бы object-array и заставил читать с `allow_pickle=True` — то есть
  исполнять пикл из файла, пришедшего от чужого агента. Это ровно та дыра,
  которой в протоколе переноса быть не должно. Теперь всё — байтовые буферы.
- numpy уже в зависимостях, отдельная библиотека не нужна.
- UTF-8 JSON читается глазами.

## 3. API

| Метод | Эндпоинт | Что делает |
|---|---|---|
| GET | `/memory/manifest` | что поедет, sha256+размеры, что не переносимо |
| POST | `/memory/export` | упаковать в `.frk1x/1` (без энкодера) |
| POST | `/memory/export_v2` | **упаковать в `.frk1x/2`** (память+энкодер+токенизатор) |
| POST | `/memory/import` | развернуть `.frk1x/1` |
| POST | `/memory/import_v2` | **развернуть `.frk1x/2`** в автономный архив |
| POST | `/memory/verify` | **независимо проверить**, что память читается |

### `/memory/export_v2`

```json
POST {"path": "G:/.../agent_a.frk1x", "include_encoder": true, "include_store": true}
→ {"ok": true, "path": "...frk1x.npz", "mb": 48.7, "s": 3.5, "sha256": "...", "manifest": {...}}
```

`np.savez` дописывает `.npz` — сервер возвращает реальный путь в `path` и
запрошенный в `requested_path`.

### `/memory/import_v2`

```json
POST {"path": "...frk1x.npz", "name": "b_archive"}
→ {"ok": true, "dir": ".../b_archive", "self_contained": true,
   "encoder": ".../encoder_w.npy", "N": 2189372}
```

**Ничего не перезаписывает.** Раскатывает новый каталог. Раскладка:

```
b_archive/
  codes.npy  cbook_l0.npy  cbook_l1.npy  ids.npy
  encoder_w.npy        <- энкодер A, работает без чекпойнта A
  tokenizer.json       <- токенизатор A, работает без путей машины A
  meta.json            <- embed_ckpt и tokenizer_file указывают на ЛОКАЛЬНЫЕ файлы
  store.json
```

Ключи `meta.embed_ckpt` и `meta.tokenizer_file` **переписываются на локальные
имена** — именно это делает архив автономным. Переключение: `FRK_IDXD=<dir>`.

### `/memory/verify` — главное

Не верит манифесту. Берёт `ids.npy` **самого пакета**, генерирует
псевдо-запросы, строит вектор тем же оператором, что и ключи
(`context-avg` окном `RAD`), гоняет ADC-only по `codes.npy` пакета и сравнивает
найденную позицию с той, откуда запрос взят.

```json
POST {"path": "<dir>", "k": 8, "n_probe": 24, "tol": 4}
→ {"recall_at_k_tol": 0.8333, "exact_in_topk": 0.7917, "verdict": "..."}
```

Допуск `tol` в токенах нужен потому, что ключи = `context-avg` окном `RAD=4`:
точечная позиция физически размыта на ~RAD. Требовать exact-попадание —
измерять ошибку самого определения ключа, а не качество переноса.

## 4. Измеренный результат (11.09.2026, 19:24–19:53 UTC)

### 4.1 Базовый перенос (frk1x/1, v8, 2 189 372 токена)

```
EXPORT   45.9 МБ, 3.5 с
IMPORT   N = 2 189 372, store восстановлен
VERIFY   recall@8 (tol=4) = 0.8333    exact_in_top8 = 0.7917
```

### 4.2 Самодостаточный перенос (frk1x/2)

```
EXPORT    48.7 МБ, 3.5 с        (+2.8 МБ за энкодер и токенизатор)
IMPORT    self_contained = true, encoder_bundled = true,
          tokenizer_bundled = true
VERIFY    recall@8 = 0.8333
```

### 4.3 Тест автономности: агент B в изоляте

Изолированный каталог `C:\...\Temp\frk_iso2` содержал **только**:
`frakod_api.py`, `frakod_mcp.py` и архив B. Ни одного файла машины A, ни одного
чекпойнта проекта, `keys_f16.npy` удалён. Запуск:

```
index_stats  → N=2 189 372, codes 50.1 МБ
recall       → ok, топ-1 по смыслу:
               "…работа агента като должна…" (позиция 25208, score 18.83)
memory_verify→ recall@8 = 0.875
```

**Это и есть доказательство переносимости:** память, её энкодер и её
токенизатор приехали одним файлом и заработали на чистой машине.

### 4.4 Что тест автономности вскрыл по дороге

Первый же прогон в изоляте **упал с `ModuleNotFoundError: final_benchmark`** —
уже после успешной загрузки кодов. Причина: `meta.json` хранил абсолютный путь
токенизатора машины A, `_archive_tok()` его не находил и молча уходил в
fallback, требующий модуль из репозитория. То есть **память приезжала, а поиск
не работал** — самый неприятный класс дефекта. Исправлено:

1. токенизатор кладётся в пакет (`_tokenizer_json`) и в архив (`tokenizer.json`);
2. `_archive_tok()` ищет сначала локально, и только потом — абсолютный путь A;
3. если архив объявлен `tokenizer_kind='external'`, а токенизатора нет —
   **внятная ошибка**, а не молчаливый fallback на чужой словарь (иначе ids
   разъезжаются и поиск выдаёт мусор с видом работающего).

## 5. Отрицательный результат: чужим энкодером память НЕ читается

Отдельный эксперимент (`exp_cross_encoder.py`, артефакт
`runs/cross_encoder_NEGATIVE_2026-09-11.md`) проверял гипотезу, что ADC-скрин
по кодобуку A сработает для запроса, построенного энкодером B.

| Кто строит запрос | recall@8 (tol=4) | 95% CI | медиана Δ |
|---|---|---|---|
| **A** (автор архива) | **0.875** | [0.75, 0.95] | 0 |
| **B** — все 15 кандидатов d=192 | **0.000** | [0.00, 0.00] | 87k – 172k |
| случайный запрос (контроль) | 0.000 | — | — |
| перемешанные коды (контроль) | 0.000 | — | — |

**Вердикт FAIL по предрегистрации.** Кодобук — производное от энкодера: 256
центроидов описывают конкретное пространство, и запрос из чужого пространства
в него не попадает. Это не «хуже», это ноль.

**Следствие для формулировки продукта (было — стало):**

| | было | стало |
|---|---|---|
| заявление | «модели разные — память общая» | «модели разные — память общая **вместе с энкодером**» |
| что едет | артефакт | артефакт + энкодер + токенизатор |
| что это даёт | «переносимость» | **автономность**: B не пересобирает память из текста и не имеет ни одного файла A, кроме самого пакета |

Заявление стало слабее, но оно **измеренное**. Это и есть цена научной
строгости: отрицательный результат закрывает соблазн сказать лишнее.

Отдельное направление, открытое этим результатом: можно ли обучить кодобук,
согласованный между энкодерами (обучать на объединённом наборе пространств
E1..Ek). Гипотеза сформулирована, проверка не начата.

## 6. Границы честности

Не прятать в мелкий шрифт — эти ограничения надо называть вслух.

1. **Энкодер и токенизатор обязательны.** Оба теперь едут в пакете (§4.3).
   Если B захочет читать своей моделью — не сработает (§5, измерено).
2. **`recall@8 = 0.83` — это не 0.83 «поиска факта».** Это восстановление
   позиции с допуском 4 токена (§5.1). Продуктовый вопрос «нашлась ли нужная
   мысль» этот тест не измеряет; для него нужен отдельный бенчмарк.
3. **Один архив, один энкодер.** Измерено на v8 (d=192). Другая размерность
   несовместима по форме — это ограничение формата, не баг.
4. **10 млн токенов не проверены.** Обещание «~280 МБ» — экстраполяция
   2.19M × 4.57. Нужен реальный архив.
5. **Транспорт — файл вручную.** Нет object-storage, хэш-адресации,
   инкрементальных дельт.
6. **`encoder_w` в float16** даёт `max|Δ| = 0.0019` против оригинала.
   На текущем recall влияния не обнаружено, но это потеря точности,
   и при ужесточении требований её придётся пересмотреть.

## 8. Что дальше (чтобы это стало достижением, а не демо)

- **10 млн токенов.** Реальный архив вместо экстраполяции.
- **Согласованный между энкодерами кодобук.** Единственный путь вернуть в
  заявление «модель B читает своим энкодером». Начато с отрицательного
  контроля — теперь есть от чего отталкиваться.
- **Инкрементальные дельты.** Дописать память, не пересылая весь архив.
- **Транспорт.** Object-storage + хэш-адресация вместо файла вручную.
- **Продуктовый бенчмарк «нашлась ли мысль»**, а не восстановление позиции.
- **Перемерить §13.6/§13.8** (цена внешнего адресного пространства) —
  те числа получены на вырожденном ключе (см. `runs/D1_CLOSED_2026-09-11.md`).

  которой в протоколе переноса быть не должно. Теперь всё — байтовые буферы.
- numpy уже в зависимостях, отдельная библиотека не нужна.
- UTF-8 JSON читается глазами (`np.load(...)['_manifest_json']` → `bytes`).

## 3. API

| Метод | Эндпоинт | Что делает |
|---|---|---|
| GET | `/memory/manifest` | что поедет, sha256+размеры, что не переносимо |
| POST | `/memory/export` | упаковать в `.frk1x` |
| POST | `/memory/import` | развернуть `.frk1x` в новый каталог-архив |
| POST | `/memory/verify` | **независимо проверить**, что память читается |

### `/memory/export`

```json
POST {"path": "G:/.../agent_a.frk1x", "include_keys": false, "include_store": true, "compress": true}
→ {"ok": true, "path": "...frk1x.npz", "mb": 45.9, "s": 3.5, "sha256": "...", "manifest": {...}}
```

`np.savez` дописывает `.npz` — сервер возвращает реальный путь в `path` и
запрошенный в `requested_path`. Не путать.

### `/memory/import`

```json
POST {"path": "G:/.../agent_a.frk1x.npz"}
→ {"ok": true, "dir": ".../frakod_index_imported_20260911_192427", "store": "...", "N": 2189372}
```

**Ничего не перезаписывает.** Всегда новый каталог. Переключение — через
`FRK_IDXD=<dir>` и рестарт API.

### `/memory/verify` — главное

Не верит манифесту. Берёт `ids.npy` **самого пакета**, генерирует
псевдо-запросы, строит вектор тем же оператором, что и ключи
(`context-avg` окном `RAD`), гоняет ADC-only по `codes.npy` пакета и сравнивает
найденную позицию с той, откуда запрос взят.

```json
POST {"path": "<dir>", "k": 8, "n_probe": 24, "tol": 4}
→ {"recall_at_k_tol": 0.8333, "exact_in_topk": 0.7917, "verdict": "..."}
```

Допуск `tol` в токенах нужен потому, что ключи = `context-avg` окном `RAD=4`:
точечная позиция физически размыта на ~RAD. Требовать exact-попадание —
измерять ошибку самого определения ключа, а не качество переноса.

## 4. Измеренный результат (11.09.2026, 19:24 UTC)

Живой прогон через HTTP API, архив `frakod_index_v8`, 2 189 372 токена.

```
EXPORT   45.9 МБ, 3.5 с          (сжатие npz; сырьё 58.8 МБ)
IMPORT   N = 2 189 372, store восстановлен
VERIFY   recall@8 (tol=4) = 0.8333    exact_in_top8 = 0.7917
```

Разбор 24 проб (первые 6):

| probe_pos | best_pos | delta | hit |
|---|---|---|---|
| 7840 | 7840 | 0 | ✅ |
| 24544 | 24544 | 0 | ✅ |
| 84445 | 84445 | 0 | ✅ |
| 87918 | 92473 | 4555 | ❌ |
| 102170 | 222885 | 120715 | ❌ |
| 102205 | 102204 | 1 | ✅ |

Средний `|delta|` = 5538 — эта цифра **не должна пугать**: она вытянута двумя
промахами из 24. Медиана `delta` = 0. Промахи — не артефакт переноса: тот же
архив даёт такие же промахи и до упаковки, потому что ключи слабые (v8-чекпойнт
имеет recall@4 = 0.00 на векторном канале). Перенос **не добавляет** ошибки.

Честная формулировка текущего статуса:

> Перенос работает и проверяется независимо. Качество поиска после переноса
> равно качеству поиска до переноса. Слабый поиск — свойство v8-энкодера,
> а не свойство переноса.

## 5. Границы честности

Не прятать в мелкий шрифт — эти ограничения надо называть вслух.

1. **Общий токенизатор или текст.** Позиции в `codes.npy` — токенные позиции.
   Если у агента B другой токенизатор, позиция указывает на другой кусок
   текста. Решение: либо общий токенизатор, либо доставать текст через
   `ids.npy` + `store.json`, а не через токенную позицию.
2. **Энкодер запроса.** Запрос агента B должен строиться тем же энкодером
   (`embed_ckpt` из `meta.json`), иначе ADC-скрин уедет. Пакет несёт
   `embed_ckpt` и `tokenizer_path` — но это **путь на диске A**, а не сам файл.
   Для настоящего переноса в чужую машину энкодер надо приложить.
3. **`recall@8 = 0.83` — это не 0.83 "поиска факта".** Это восстановление
   позиции с допуском 4 токена. Продуктовый вопрос «нашлась ли нужная мысль»
   этот тест не измеряет; для него нужен отдельный бенчмарк.
4. **Один архив, один энкодер.** Пока измерено только на v8. Перенос между
   *разными* энкодерами (модель A пишет, модель B читает своим энкодером) —
   это другой эксперимент, и он ещё не поставлен.

## 7. Что дальше (чтобы это стало достижением, а не демо)

- **Энкодер в пакет.** Сейчас `embed_ckpt` — путь. Нужно вкладывать сам
  чекпойнт (или ссылку с хэшем) — иначе агент B не воспроизведёт запрос.
- **Разные энкодеры.** Поставить эксперимент: A пишет `codes.npy` энкодером
  E1, B читает, строя запрос энкодером E2. Если recall падает не сильно —
  это и есть настоящая переносимость, а не тавтология «тот же кодек читает
  тот же кодек».
- **10 млн токенов.** Прогнать 10M → проверить обещание «~280 МБ» на реальном
  архиве, а не экстраполяцией 2.19M × 4.57.
- **Транспорт.** Файл вручную — это не продукт. Нужны object-storage,
  хэш-адресация, инкрементальные дельты (дописать память, не пересылая всё).
