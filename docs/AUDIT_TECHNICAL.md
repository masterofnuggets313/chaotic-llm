## 1. D1 — Вырожденность внешнего адресного пространства

### 1.1 Механика

`external_keys(ids, nsub, dim)` в `exp_transferable_memory.py:128` и
`exp_transfer_crossarch.py:198`:

```python
sub = d // int(nsub)                 # 192 // 12 = 16
h   = (token * 2654435761 + (off + half) * 40503) & 0x7FFFFFFF
idx = (h % sub)                      # 0 … 15
col = idx % sub                      # 0 … 15   ← тождественно idx
np.add.at(out, (rows, col), sgn)
```

`col` лежит в `[0, sub)` при любом токене и любом `offset`. **Индекс подпространства
не вычисляется нигде.** Параметр `nsub` влияет на ключ исключительно через `sub = d // nsub`.

### 1.2 Измерение (воспроизводимо)

```
nsub=12 → ненулевых координат из 192 = 16   ; eff. rank = 16
nsub=6  → ненулевых координат из 192 = 32   ; eff. rank = 32
nsub=1  → ненулевых координат из 192 = 192  ; eff. rank = 192
```

Следствия, зафиксированные в `FRAKOD_STATUS_2026-09-11_v2.md` §13.9:
из 12 подвекторов PQ (S=12 по 16 координат) информативен **один**;
**22 из 24 байт на ключ квантовали точные нули**.

### 1.3 Критическое замечание к доказательной базе

Утверждение статуса «все новые прогоны — с `--nsub 1`» **не подтверждается кодом и
артефактами**:

1. Дефолт `--nsub` остался **12** в обоих ключевых инструментах сквозного прохода:
   `exp_transfer_crossarch.py:314`, `_e2e_ext_keys_strat.py:98`.
2. **Ни один артефакт не содержит `nsub`.** Проверено:
   `runs/e2e_dialog_strat.json`, `runs/e2e_mixed_strat.json`, `runs/e2e_sts_strat.json`,
   `runs/e2e_dialog_ceiling.json`, `runs/ho_dialog_stack.json`,
   `runs/ho_dialog_public.json`, `runs/ho_mixed_stack.json`, `runs/ho_sts_stack.json` —
   ключа `nsub` нет.

**Вывод.** Числа §13.6 / §13.8 / §4.6 / §4.8 (цена внешнего адресного пространства
+0.148…+1.840 нат) **не верифицируемы по предъявленным артефактам**: невозможно
установить, получены ли они на вырожденном ключе (`nsub=12`) или на полном (`nsub=1`).
Это блокирует публикацию именно этого результата — и именно он объявлен главным
дифференциатором (§4 плана).

### 1.4 Правка

```python
# было
col = idx % sub
# должно быть: задействовать индекс подпространства
nsub_i = (h // sub) % nsub                 # какое подпространство
col    = nsub_i * sub + (h % sub)          # абсолютная координата в [0, d)
```

Обязательные сопутствующие изменения:
* `--nsub` дефолт → `1` (полный ранг) либо явная остановка, если `nsub > 1`;
* запись `nsub`, `window`, `dim`, `seed` в **каждый** артефакт;
* перезамер всех зависимых чисел §13.6/§13.8 заново — старые помечать
  «на вырожденном ключе, не сравнивать с новыми».

## 2. D2 — `recall_adc_only` игнорирует `kcand`

`frakod_api.py:383`:

```python
def recall_adc_only(qvec, k_return=8, kcand=65536):
    ...
    kk = min(k_return, N)              # ← kcand не читается
    top = np.argpartition(-adc, kk)[:kk]
    ...
    return {..., 'kcand': int(kk), 'ranking': 'adc_only'}
```

`kcand` не используется; в ответ пишется `'kcand': k_return`. Вызов
`/recall?mode=vector24&kcand=65536&k=8` вернёт `kcand: 8` — и это же число будет
прочитано любым замером как «сколько кандидатов проверено».

**Правка.** Убрать `kcand` из сигнатуры ADC-пути либо честно сообщать
`screened`/`returned` и не подменять поля. Публичный контракт `/recall`
обязан быть единым для `vector` и `vector24` — сейчас он разный.

## 3. D3 — API требует `keys_f16.npy`, хотя продукт живёт на ADC

`frakod_api.py:319` (`load_index`):

```python
codes = np.load(os.path.join(IDX_DIR, 'codes.npy'), mmap_mode='r')
keys  = np.load(os.path.join(IDX_DIR, 'keys_f16.npy'), mmap_mode='r')   # ← безусловно
```

Билдер (`frakod_index_build.py:118`) штатно собирает архив **без** `keys_f16` при
`FRK_NO_KEYS=1`, и это **рекомендованный дефолт для продукта** (реранк измеренно
вредит, `_adc_vs_rr.py`). Такой архив:

* `/recall?mode=vector24` — работает (keys не нужен);
* `load_index()` — **падает** на `np.load`, то есть сервер не стартует.

Эталон корректной реализации — `frakod_chunk_index.py:182`:

```python
kp = os.path.join(path, 'keys_f16.npy')
idx['keys'] = np.load(kp) if os.path.exists(kp) else None
```

**Правка.** Сделать `keys` опциональным во всём стеке `frakod_api.py`:
`load_index`, `_to_gpu` (не переносить `keys`/`mu` при `None`), `_recall_gpu`,
`_recall_cpu`, `recall_vec`. При `keys is None` любой режим должен деградировать
в ADC-only, а не в исключение.

## 4. D4 — Два канонических пути ADC

| Функция | Нормализация запроса |
|---|---|
| `recall_adc_only` (`:383`) | **нет** — и в docstring объявлено, что нормировать нельзя |
| `_recall_gpu` (`:346`) | **да** — `q = q / (q.norm() + 1e-9)` |

Проверка на живом архиве `frakod_index_v8`:

```
|q_raw| = 4.643
corr(adc(q), adc(3q)) = 1.000000
corr(adc(q), adc(0.2q)) = 1.000000
top-16 overlap: 16/16, 16/16
норма ключей: min 3.910, медиана 4.621, max 9.081
```

**Вывод.** ADC строго линеен по `q`; масштаб **не влияет на ранжирование**.
Противоречие в коде на сегодня **безвредно**, но является латентным дефектом:
любое нелинейное расширение пайплайна (клиппинг, порог, fusion с лексикой) сделает
разные режимы несравнимыми.

**Правка.** Оставить **один** путь и закрепить инвариант тестом
(`test_adc_rank_invariance`): ADC-ранжир инвариантен к положительному масштабу `q`.

## 5. D5 — Переносимая память как артефакт отсутствует

### 5.1 Что есть

* `ingest_chat.py` — **импорт** выгрузок (`a`/`b`/jsonl/txt`) → текстовый дамп → архив.
  Односторонний.
* `exp_transferable_memory.py`, `exp_transfer_crossarch.py` — научные инструменты
  переноса (адресация архива).
* `frakod_mcp.py` — 8 инструментов памяти.

### 5.2 Чего нет

* контракта артефакта памяти (`mem.frk`: коды + мета + манифест + версия + sha256);
* `/export`, `/import` в API;
* проверки совместимости при импорте (пространство ключей, энкодер, токенизатор, S/K/d);
* **критерия приёмки** «А записал → Б прочитал без дообучения».

### 5.3 Установленное условие переносимости (§4.5, §4.7 статуса)

Наивная схема («архив между чекпойнтами») **опровергнута**: ключ `embed(x) + pos`
приходит из обучаемых весов, у двух моделей один и тот же текст даёт
**ортогональные** векторы (cos = **0.0029**), перенос физически не определён.

Переносится **внешнее адресное пространство**: ключ — детерминированная функция
токенов. Тогда архитектура приёмника безразлична, и `recall@8 = 0.797` при 24 Б/ключ
вместо 0.000 (шаг 3.1). **Но** это число получено на ключе, чья размерность под
вопросом (D1) — требует перезамера.

### 5.4 Минимальный контракт (предлагаемый)

```
frk export --index <dir> --out mem.frk
  manifest.yaml: {format_version, encoder{name,dim,hash}, key_space{nsub,window,seed},
                  codec{L,S,K}, tokenizer{path,sha256}, corpus{sha256,n_tokens},
                  bytes{...}, checksum}}

frk import mem.frk --into <dir>
  отказ, если не совпали: encoder.hash | key_space | codec.L,S,K | tokenizer.vocab
```

Это то, что делает память **самостоятельным артефактом**, а не частью весов.

## 6. D6 — Артефакты не самодостаточны

Ни один из проверенных JSON-артефактов не содержит полного набора параметров
прогона. Минимально необходимый набор:

`ckpt` (абсолютный путь + sha256), `tokenizer` (+sha256), `corpus` (+sha256, n_tokens),
`W`, `M`, `n_keys`, `strata`, `nwin_per_stratum`, **`nsub`**, `window`, `S`, `K`, `L`,
`seed`, `mode`, версия инструмента, время.

Без этого «число» не является научным результатом — оно не воспроизводимо.
Именно здесь возник D1.3: параметр потерян, и результат повис.

**Правка.** Единый хелпер `write_artifact(path, cfg, payload)` — принудительно
дописывает `cfg` в каждый JSON; тест, что в сохранённых артефактах ключи присутствуют.

## 7. D7 — Воспроизводимость внутримодельного кодбука

* Причина установлена: `fracode_memory_probe.kmeans` накапливает суммы через
  `index_add_` = CUDA `atomicAdd`; порядок сложения float не определён.
* Симптом: разброс Δ до **0.0342 нат** (медиана 0.0066) при одном сиде.
  Порог вердикта — 0.05 нат. Шум того же порядка.
* Частичный фикс сделан (centering + `cumsum` в float64, `fracode_memory_probe.py:87–108`):
  `_ab_det_seed0` == `_ab_det_seed0_rep`, `exact_ppl = 1317.103299` во всех 5 прогонах.
* **Остаток:** необъяснённый разброс **0.016 нат** при смене набора `--variants`
  (FR-8x: 1209.5 против 1228.8 при идентичном `exact`).

**Статус:** запрещено писать «воспроизводимость решена». Допустимо:
«устранена основная компонента невоспроизводимости (atomicAdd); остаточный разброс
0.016 нат при смене `--variants` не объяснён».

**Правка до публикации.** Локализовать остаток; проверить, не переиспользуется ли
состояние фита между вариантами.

## 9. D9 — Дефолтный путь архива не существует

`frakod_api.py:301`:

```python
IDX_DIR = os.environ.get('FRK_IDXD') or os.path.join(os.path.dirname(os.path.abspath(__file__)), 'frakod_index')
```

Каталога `frakod_index` **нет**. Реально существуют `frakod_index_v7` и `frakod_index_v8`.
`frakod_index_build.py:38` кладёт архив в `frakod_index` по умолчанию — но ни одного
архива там нет, потому что все прогоны задавали `FRK_OUTD` вручную.

**Следствие.** Ни `/recall`, ни MCP не работают «из коробки» после чистого клона
репозитория: нужен `FRK_IDXD`. При этом `frakod_index_build.py` создаёт
`frakod_index` — то есть после **первой сборки** путь внезапно становится верным.
Это классическая ловушка: работает у того, кто уже собирал архив, и не работает
у того, кто скачал и запустил.

**Правка.** Автопоиск: `FRK_IDXD` → `frakod_index` → последний по `built_utc` из
`frakod_index_v*`; либо явное внятное сообщение «архив не найден, укажите FRK_IDXD».
README (строка 138) обязан упоминать, что дефолт — без суффикса.

## 10. Что НЕ доказано (явный перечень)

| Утверждение | Состояние | Причина |
|---|---|---|
| Модель с Fracod-памятью ≥ KV при равной памяти | **не показано** | W=262k на 16 окнах → CI ±0.5 нат; знак не воспроизвёлся |
| Паритет по скорости с KV | **опровергнуто** | 1.63× (fast ADC, +2.2% PPL) … 5.2× (точный) медленнее |
| Fracod > PQ | **снято** | на разрешимом бенчмарке — ничья |
| 64× без потери recall@4 | **снято** | n=207: 0.517 → 0.435, −0.082; воспроизведено на 2 энкодерах |
| Перенос A→B без дообучения | **не проверено end-to-end** | измерена адресация, не ответ; ключ на вырожденном пространстве |
| Space-filling curves / FRVQ | **сняты** | ID(остаток) = 2×ID(сигнал); лучшая кривая 87.4% против 100% у ADC |

**Основной положительный результат, который защитим:**

> Сжатие ключей 8–32× статистически не отличимо от точной памяти по log-loss
> (Δ = −0.0130 / +0.0041 / +0.0022 нат, 5 чекпойнтов, предрегистрированный вердикт).
> Сжатие плотного ретривера 64× стоит ≈0.08 recall@4 (0.517→0.435, n=207, SE≈0.034,
> воспроизведено на bge-m3 и snowflake-arctic-embed2).

## 11. Программа вклада (приоритеты)

### Приоритет 0 — доказательная база (часы)

1. D1 — починить `external_keys`; `--nsub` дефолт 1; перезамер §13.6/§13.8.
2. D2 — `kcand` в ADC-пути.
3. D3 — опциональный `keys_f16` в API.
4. D6 — хелпер записи конфигурации в артефакты.
5. D7 — доразобрать 0.016 нат.
6. D8 — привести документацию к фактам.

### Приоритет 1 — переносимая память (недели) — **уникальный вклад**

Реализовать `export`/`import` (D5) поверх внешнего адресного пространства.
Критерий приёмки: А записал → Б (другая архитектура, другая инициализация) читает
без дообучения, выигрыш на удержанных данных, честный CI.

Почему это и есть вклад: это единственная формулировка, где память **перестаёт
принадлежать модели** — не нужен KV на инференсе, не нужна передача состояния между
инстансами, память масштабируется независимо от весов, команда делит память между
агентами. У крупных лабораторий опубликованного результата здесь нет.

### Приоритет 2 — масштаб и честный длинноконтекстный протокол

Контекст ≥256k, ≥64 окна на конфигурацию, параметрический **и** memory-матч,
обязательная колонка `bytes/token` и `decode tok/s`. Требует решения владельца
по GPU 24–48 ГБ.

### Приоритет 3 — продукт

Внешний энкодер (bge-m3-класс) как дефолт, гранулярность чанк, память как отдельный
сервис со сменным LLM-клиентом. Уже частично сделано в `frakod_chunk_index.py` —
его подход (независимость от словаря модели) должен стать нормой для `frakod_api.py`.
