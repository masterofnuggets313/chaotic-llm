## Эксперимент B — корпус как причина слабой семантики

### Гипотеза H-B

v8-чекпойнт не связывает русский ВОПРОС со сниппетом (recall@4 = 0.00) и различает
разные русские тексты на cos = **0.284** вместо обещанных docstring'ом **0.04**.
Причина — `build_corpus()` разбавляет русский диалог 200 МБ кода
(`corpus_stack_train.txt`) при апвейте истории всего ×4.

**Предсказание:** тот же рецепт на диалоговом корпусе БЕЗ code-добавки вернёт
различимость к уровню ≲ 0.10.

### Условия (зафиксированы)

| | диалог (H-B) | смешанный (контроль) |
|---|---|---|
| корпус | `hermes_history_dd.txt` + `hermes_history.txt` | исходный `build_corpus()` 1:1 |
| чекпойнт | `v8_dialog_seed{0,1}.pt` | `v8_mixed_seed0.pt` |
| токенизатор | `tok_v8_dialog.json` | `tok_v8_mixed.json` |
| шагов / batch | 40000 / 48 | 40000 / 48 |
| lr / warmup / clip | 3e-4 / 1200 / 1.0 | то же |
| W / модель | 256 / PurePCLM d=192 l=8 | то же |
| сиды | 0 и 1 | 0 |
| отбор чекпойнта | по val_ppl (`corpus5m_test.txt`) | то же |

Рецепт НЕ меняется. Меняется ТОЛЬКО состав корпуса — это и есть предмет.

### Вердикт (до прогона)

* **Различимость** (cos между разными текстами, тот же оператор, что в
  `_diag_v8_vector.py`):
  - **ПОДТВЕРЖДЕНО**: `dist_mean ≤ 0.10` на диалоговом корпусе И контроле `mixed`,
    где ожидается прежний уровень (≳ 0.2).
  - **ОПРОВЕРГНУТО**: `dist_mean > 0.15` на диалоговом корпусе — корпус не причина,
    копать архитектуру.
  - **ПРОМЕЖУТОЧНО**: 0.10 < `dist_mean ≤ 0.15` — эффект есть, но недостаточен.
* **Контроль `mixed`** обязателен: он отделяет эффект корпуса от «я просто обучил
  заново». Если mixed тоже даст ≤ 0.10 — значит дело не в корпусе, а в чём-то ещё
  изменившемся (сиды/отбор), и B не считается подтверждённым.
* **Разрешение неопределённого случая для `mixed` (зафиксировано 11.09, 14:50,
  ДО финальных чисел).** Формулировка «≳ 0.2» не является числом, поэтому вводится
  правило чтения, не меняющее порог диалога (0.10 / 0.15 остаются как есть):
  - `mixed ≥ 0.20` → контроль выполнен, вердикт по диалогу выносится буквально.
  - `0.10 < mixed < 0.20` → **эффект корпуса признан, но не полным.** Диалог при
    `≤ 0.10` получает «ПОДТВЕРЖДЕНО ЧАСТИЧНО: корпус объясняет большую часть
    разрыва (0.284 → mixed), остаток — за архитектурой/сидом». Это НЕ полное
    подтверждение H-B, в публикацию идёт с этой оговоркой.
  - `mixed ≤ 0.10` → контроль НЕ разделяет причины; H-B не подтверждён
    (как и написано выше), ищем иное объяснение.
  Правило действует для seed0 контроля; при нескольких сидах — по среднему.
* **val_ppl** — вторичная метрика. Ожидание: диалоговый ниже (корпус проще, один домен).
  Если он ВЫШЕ смешанного значимо — рецепт на диалоге хуже, B не рекомендуется к масштабу.

### Запреты

Не интерпретировать числа до первого val-шага на 2000. Не сглаживать: `dist_mean`печатать как есть. Сравнивать только пары «диалог vs смешанный» при **одном**
`select_by`, одном val-корпусе, одном числе шагов.

**Следствия для линии проекта:**

1. **Корпус — причина, а не архитектура.** Слабая семантика v8 (0.284) объясняется

   диалоге тот же рецепт, та же архитектура и тот же оператор дают 0.057…0.072 —

2. **Обещание «~0.04» близко, но не достигнуто.** 0.057 (s1) против ~0.04 из

3. **val_ppl диалога НЕ ниже.** Ожидание из предрегистрации («диалог проще») не

   4-12 раз выше по val_ppl. Причина: mixed-корпус содержит код, а val-корпус
   тот же смешанный, поэтому диалоговая модель на нём штрафуется сильнее.
   Прямое следствие: **val_ppl на смешанном val нельзя использовать для выбора
   между диалоговой и смешанной моделью** — метрика и корпус не согласованы.
   Это ограничение метода сравнения, а не результат о качестве моделей.
4. **Вторичная находка (подтверждает §13.5):** у диалоговых сидов CI различимости
   накрывают 0 (−0.103…0.206 и −0.048…0.262), у mixed — нет (0.247…0.449).
   То есть диалоговый уровень 0.065 статистически неотличим от нуля на 20 точках,
   тогда как 0.348 — устойчиво положителен.

Оговорка: n = 2 сида у диалога, n = 1 у контроля. Разделение 0.065 против 0.348
огромно (5.4×) и покрыто непересекающимися CI, но формальное подтверждение
на 3+ сидах не выполнено. В публикацию идёт с этой оговоркой.

## Эксперимент T — переносимая память (этап 3.1)

> **ИТОГ ЭКСПЕРИМЕНТА T (11.09.2026, 15:45): ДВА РЕЗУЛЬТАТА.**
> (1) Наивная формулировка «общий кодбук + ключи из весов» — **ОПРОВЕРГНУТА**
> (`transfer = 0.000`, причина — cos = 0.0029, ключи приходят из весов).
> (2) Переформулированная «память через ОБЩЕЕ пространство ключей» — **ПОДТВЕРЖДЕНА**
> (`recall@8 = 0.797` при 24 Б/ключ; сжатие 16× → 0.861 на архиве 60k).
> Детали обеих частей — ниже; не читать нулевой вердикт как единственный.

### Гипотеза H-T

Архив (коды ключей `e = embed(x) + pos`, сжатые Fracod-кодбуком) **переносится между
моделями одного семейства**: модель B, не обучавшаяся на архиве A, читает его.

Это единственный уникальный дифференциатор: если работает — память отделяется от
модели (архив становится транспортабельным артефактом).

### Условия (зафиксированы)

| | значение |
|---|---|
| источник A | `v8_dialog_seed0.pt` (линия vocab=8192) |
| приёмники B | `v8_dialog_seed1.pt` (+ остальные сиды, если появятся) |
| архив | `hermes_history_dd.txt`, `bits` фиксируется в отчёте |
| ключи | `static_keys` = `embed(ids_windows) + pos`, окна W=256 |
| кодбук | `StreamFracode(d=192, L=2, S=12, K=256)`, det=True, 24 Б/ключ |
| метрика | recall@8 «своя позиция в top-8 по ADC-скрину» |
| запросов | nq ≥ 64, позиции вне первых/последних 64 токенов |
| сид выбора позиций | 7 |

**Три режима (обязательны все три):**

| режим | кодбук обучен на | кодируются ключи | читает | смысл |
|---|---|---|---|---|
| 1 `own_arch` | B | B | B | baseline приёмника |
| 2 `transfer` | **A** | **A** | **B** | **ПЕРЕНОС** |
| 3 `cross_fit_cbook` | B | A | B | контроль: помогает ли переобучение |

### Вердикт (до прогона)

Сравнение режима 2 против режима 1, среднее по приёмникам:

* **ПЕРЕНОСИТСЯ**: `transfer ≥ 0.8 × own_arch` И `transfer > 0.5`.
* **ЧАСТИЧНО**: `0.2 < transfer < 0.8 × own_arch` — формулировать как «перенос
  возможен при условии X», X искать в режиме 3.
* **НЕ ПЕРЕНОСИТСЯ**: `transfer ≤ 0.2`. Отрицательный результат; публикуем как есть
  и переходим к поиску общего компонента (общий кодбук? общий G(e)?).

**Разрешение.** Запросов nq ≥ 64; при `own_arch` около 0.2 разница 0.1 различима,
меньше 0.05 — нет. Значит формулировки вида «переносится на 5%» запрещены: только
«в пределах разрешения не обнаружено».

### РЕЗУЛЬТАТ (выполнено 11.09, 14:48, на промежуточных чекпойнтах ~16k/40k)

Запуск: `--src 0 --dst 1 --pattern "v8_dialog_seed{}.pt" --bits 8192 --nq 64`
(32 окна — тот же размер, что дал калибровку потолка 0.531).

| режим | recall@8 |
|---|---|
| `own_arch` (B читает свой архив) | **0.516** |
| `transfer` (B читает архив A) | **0.000** |
| `cross_fit_cbook` (кодбук B, ключи A) | **0.000** |

**ВЕРДИКТ: НЕ ПЕРЕНОСИТСЯ.** `transfer = 0.000 ≤ 0.2` — нижняя ветка предрегистрации.
Причём это не «хуже», а **ровный ноль**: ни один из 64 запросов не нашёл свою позицию,
и контроль `cross_fit_cbook` тоже ноль — переобучение кодбука не помогает.

**Причина установлена прямой диагностикой** (`_diag_transfer_zero.py`), а не догадкой:

| величина | значение |
|---|---|
| cos(ключ позиции: тот же текст, модель A vs B) | **0.0029** |
| cos между разными позициями внутри A | 0.0054 (средн.), **0.9987 (макс.)** |
| argmax по своим ключам | **256/256** |
| argmax по чужим ключам | **3/256** |

`e = embed(x) + pos` — это **веса конкретной модели**. У сида 0 и сида 1 таблицы
`embed` разные, поэтому один и тот же текст отображается в **ортогональные** векторы
(cos ≈ 0.003). Архив, собранный моделью A, для модели B — набор чужих адресов.
Перенос в формулировке «общий кодбук + общие ключи» **невозможен по построению**;
это свойство не Fracod, а того, что ключи берутся из обучаемых весов.

**Что следует (и это ценно):** переносимая память требует **общего пространства
ключей**, независимого от весов конкретной модели. Кандидаты для следующей итерации
(предрегистрировать до запуска):
1. **Общий внешний энкодер** (как в `frakod_chunk_index.py`, bge-m3): ключи приходят
   извне `embed`, архив переносим по построению; надо показать, что модель умеет
   читать внешние ключи.
2. **Дистилляция адресного пространства**: обучить B выравнивать ключи на ключи A
   отдельным лоссом, затем проверить перенос.
3. **Общий замороженный `embed` первой ступени** — ключи становятся совместимыми.

### РЕЗУЛЬТАТ кандидата №1 (общее пространство ключей) — выполнен 11.09, 15:41

Формулировка «перенос через ОБЩЕЕ пространство ключей»: ключ — детерминированная
функция ТОКЕНОВ (хешированные вклады окна ±8 токенов, `external_keys()`), а не
`embed(x) + pos`. Раз он не зависит от весов, обе модели адресуют одну точку.

**Сначала был ложный «успех», и его удалось отловить.** Первая реализация хешировала
только 3-граммы. Она дала `recall@8 = 0.453`, но диагностика показала: **уникальных
ключей 23.8 %** (1947 из 8192) — остальное коллизии. При бюджете 8 позиций из 8192
recall≈8/8192 держится на одних коллизиях, то есть число не означает ничего.
После перехода на оконный ключ: **уникальных 100 %** (замерено на 8k и 60k).

**Итог на финальных чекпойнтах 40k** (`transfer_v8_dialog_ext.json`):

| режим | recall@8 |
|---|---|
| `own_arch` (ключи из весов, свой архив) | 0.547 |
| `transfer` (ключи из весов, чужой архив) | 0.000 |
| **общее пространство ключей** | **0.797** |

**Бюджетная кривая** (`_ext_key_space.py`, 4 кодбука на точку, ±sd):

| архив | Б/ключ | сжатие | recall@8 | ±sd |
|---|---|---|---|---|
| 7 781 | 384 | 2.0× | 1.000 | 0.000 |
| 7 781 | 96 | 8.0× | 1.000 | 0.000 |
| 7 781 | 48 | 16.0× | 1.000 | 0.000 |
| 7 781 | 24 | 32.0× | 0.883 | 0.036 |
| 7 781 | 12 | 64.0× | 0.883 | 0.036 |
| 60 254 | 96 | 8.0× | 0.992 | 0.000 |
| **60 254** | **48** | **16.0×** | **0.861** | 0.024 |
| 60 254 | 24 | 32.0× | 0.332 | 0.026 |

Вердикт (честный):
* **Переносимость достигнута по построению** — но не «памятью Fracod», а тем, что
  адресное пространство перестало зависеть от весов. Это ровно то, что предсказала
  причина нуля (cos = 0.0029 у ключей из весов).
* **Цена сжатия реальна и растёт с размером архива.** На 7.8k ключей 16× бесплатно;
  на 60k ключей 16× стоит −0.131 (0.992 → 0.861), 32× уже ломается (0.332).
* **НЕ смешивать с основной линией.** Точка отсчёта здесь — внешний ключ fp32
  (768 Б), а не `keys_f16` модели (384 Б). Числа этой таблицы несопоставимы с §12
  и с кривой памяти→recall из `CALIBRATION_memory_vs_recall.md`.
* **Оговорка:** метрика — self-retrieval (найти собственную позицию), а не ответ на
  вопрос по тексту. Она проверяет адресацию, а не семантику.

**Что осталось для полного подтверждения:**
1. Модель должна УМЕТЬ ЧИТАТЬ внешние ключи (`embed` на входе прямого прохода) —
   сейчас проверена только адресация архива, а не сквозной ответ.
2. n = 60k ключей, 128 запросов, 4 кодбука. 32× ломается при этом размере — нужен
   фиксированный протокол на большем объёме.
3. Смешанный архив (две модели пишут в один архив) — прямая проверка сценария
   «общая память команды».

Пункт 1 — самый дешёвый и уже реализован в продуктовом тракте; он первый кандидат.
Отрицательный результат не отменяет ценность эксперимента: он меняет формулировку
с «память переносится между моделями» на **«память переносится через общее
пространство ключей»** — а это проверяемо и остаётся уникальным.

**Оговорка о статусе чекпойнтов:** прогон сделан на промежуточных ~16k/40k. Он
корректен как тест переноса (ортогональность пространств — следствие разных `embed`
и от числа шагов не зависит), но `own_arch` 0.516 может измениться к 40k. Перепрогон
на финальных чекпойнтах обязателен; ожидаемое изменение — только в `own_arch`,
вердикт `not_transferable` от него не зависит.

**Побочная находка (важная для H-B):** cos между РАЗНЫМИ позициями внутри модели
достигает **0.9987**. То есть модель едва разделяет позиции — своя находится
(argmax 256/256), но на фоне почти единичного сходства со всеми прочими. Это
независимое подтверждение того, что чекпойнт ещё семантически слаб, и согласуется
с H-B. Число 0.9987 стоит включить в отчёт как ещё один индикатор качества
представлений, независимый от различимости по пробам.

### Действующее ограничение (записано до прогона)

Линия v7 (vocab=512) для этого эксперимента **непригодна**: на русском корпусе
клиппируется ~45% токенов, архив вырождается. Это не мнение, а измеренный факт
(смоук на `sts_prog_seed0/1`). Эксперимент T имеет смысл только на линии vocab≥8192,
то есть требует **двух** чекпойнтов Варианта B. Скрипт это проверяет и отказывается
работать при клиппировании > 10% (`return 3`).

   смешанный — втрое выше. Это согласуется с H-B, но результатом считается только
   **финальное** значение после 40k шагов, а не раннее.

2. **Контроль `mixed` критичен и ещё не дал числа.** Если смешанный корпус при
   инициализации тоже покажет ≲0.1, а после обучения вырастет до 0.28 — значит корпус
   не «ломает» семантику сам по себе, а именно разбавляет её в процессе обучения.
   Формулировка вердикта в силе; добавляю обязательную строку отчёта:
   `dist(init) / dist(step2000) / dist(final)` для обоих корпусов.

## Дополнение от 11.09.2026, 14:42 (до конца прогонов, рамки не двигаю)

3. **Потолок метрики зависит от размера архива — сравнивать только при равном `n_win`.**
   Проведена калибровка измерителя (self-check, приёмник = источник) на трёх размерах:

   | окон `n_win` | токенов | потолок recall@8 |
   |---|---|---|
   | 4 | 1 024 | 0.812 |
   | 32 | 8 192 | 0.531 |
   | 128 | 32 768 | 0.406 |

   ADC-скрин теряет точность с ростом числа кандидатов, поэтому потолок падает.
   Следствие, обязательное к учёту: **число `transfer` само по себе невердиктно** —
   оно читается как доля от потолка при ТОМ ЖЕ `n_win`. Порог раздела «переносится»
   (`transfer ≥ 0.8 × own_arch`) не меняется, но в отчёт добавляется колонка
   `transfer / ceiling` и явное указание `n_win`. Формулировки без `n_win` запрещены.

4. **Self-check не является вердиктом.** Обнаружено и исправлено: при `--self-check`
   скрипт печатал «ВЕРДИКТ: переносится», хотя приёмник = источник по построению.
   Теперь self-check пишет `"mode": "self_check"`, `"verdict": null`, `"ceiling": …`.
   Это закрывает возможность предъявить калибратор как результат H-T.

5. **Проверка условия сравнения: конкуренция за GPU симметрична.** Прогоны идут
   параллельно (диалог ×2 + mixed ×1 + бенчмарк), и это вызывало опасение, что
   контроль зашумлён. Измерено: скорость у всех трёх тренировочных прогонов
   **одинакова — 0.116 с/шаг** (по последним 4 интервалам на 11.09, 14:44).
   Следствие: замедление равномерное, число шагов одинаковое, поэтому сравнение
   «диалог vs mixed» по различимости остаётся корректным; перезапускать контроль
   **не требуется**. Условие зафиксировано, чтобы перепроверяемое сравнение не
   поднимало этот вопрос заново.

## Приложение: бенчмарк для §13.1 (зафиксировано до измерения)

`§13.1` v2 оставил прямой вопрос: на 64 Б итог зависит от ветки — **0.545 (ADC)
против 0.636 (rerank)** при n = 33, SE ≈ 0.085, и разрешить это «нельзя, нужен

через `qwen3.5:9b`. Те же поля (`query`, `snippet`, `char_pos`), тот же корпус.
SE падает ≈ 0.085 → 0.034.
