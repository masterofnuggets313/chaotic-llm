# Fracode Memory Layer — сжатие памяти STS-Prog

**Дата:** 2026-09-02 · RTX 3060 12 GB · **Скрипт:** `fracode_memory_probe.py`
**Память:** реальный обученный чекпоинт `results/ckpts/sts_prog_seed0.pt` (vocab=512, d=192, L=8, topk=8),
запросы построены из реального текста TinyStories. W=262 144, 24 запроса, M=1024 кандидатов.

## Что проверялось

Гипотеза коллеги Германа: сжимать не модель, а **память** (ключевую таблицу `(W,d)`),
иерархически, с прогрессивным восстановлением.

**Критическое отличие от «просто сжатия»:** экономия VRAM есть ТОЛЬКО при поиске
**в сжатом домене** (ADC) с восстановлением лишь отобранных кандидатов. Если ради top-k
разворачивать всю `(W,d)` обратно — VRAM остаётся 7.3 GB.

## Маппинг Fracode → память модели

| Fracode | Память модели |
|---|---|
| Library (общая библиотека генераторов) | кодбук центроидов, обученный на корпусе |
| Instructor (иерархическое дерево сборки) | коды `(уровень l, подвектор s)` |
| Прогрессивная реконструкция | `x ≈ Σ_l decode_l(codes_l)` — остаточные уровни |
| O(1) random access | код позиции независим, декод позиции без остальных |
| Генератор (детерминированная функция) | центроид (детерминирован, воспроизводим) |

**Честно про приоритет:** ядровой механизм (кодбук + ADC) = **product quantization**
(Jégou et al. 2011, FAISS) — это PRIOR ART. Fracode-вклад, который здесь проверяется, —
**иерархическое остаточное уточнение (L>1)**. Проверка корректна только при **равном бюджете байт**
(урок Fracode Phase 0: они проиграли zstd+dict, измерив конкурента криво).

**Метрики:** `recall@M` — доля истинного top-8, попавшая в ADC-кандидаты (скрининг);
`final@k` — совпадение множества после точного переранка 1024 кандидатов;
`driverCos` — косинус между driver'ом (взвешенной суммой top-k, **тем, что реально ест модель**)
из сжатой памяти и из точной.

## Выводы

### 1. Иерархия Fracode (L=2) бьёт flat PQ при равном бюджете байт

| bytes/pos | flat PQ L=1 | FRACODE L=2 | Δ |
|---|---|---|---|
| 96 (8×) | 84.9% / cos 0.987 | **87.0% / cos 0.992** | +2.1 п.п. |
| 48 (16×) | 58.3% / cos 0.975 | **64.6%** / cos 0.966 | +6.3 п.п. |
| 24 (32×) | 30.7% / cos 0.919 | **41.7% / cos 0.950** | +11.0 п.п. |

Гипотеза подтверждена: «матрёшка» — не переименование PQ. На 32× выигрыш +11 п.п. по
final@k и +0.031 по driverCos.

### 2. Скрининг работает почти идеально даже при сильном сжатии

`recall@M` держится 97–100% вплоть до 32× (L=2) — сжатый домен надёжно **находит нужный
участок**, теряется лишь точный порядок при переранке. Это ровно то, что предсказывал коллега:
«coarse → нашли регион → раскрыли следующий уровень».

### 3. Driver (то, что ест модель) сохраняется

`driverCos` = 0.950 на 32×, 0.966 на 16×, 0.992 на 8×. То есть вход блока PC-синхронизации
почти не отличается от точного, даже когда точное множество top-8 совпадает лишь на 41.7%.

### 4. Главный результат для VRAM

**10M токенов контекста → 229 МБ вместо 7324 МБ (32×)** при driverCos 0.950.
Это снимает лимит `width=192`: при 32× та же 12-GB карта держит уже не 10M, а сотни миллионов
токенов по памяти (упираться начнёт уже скорость, а не VRAM).

## Честные ограничения

1. **На 4× обычный int8 ЛУЧШЕ и дешевле** (99.0% vs 97.4–98.4%). Fracode/PQ имеет смысл
   **от 8× и выше** — там, куда int8 физически не может пойти. Это честная ниша.
2. **final@k деградирует сильно** (41.7% на 32×): точное множество top-8 восстанавливается плохо.
   driverCos высокий, но это прокси-метрика.
3. **Не измерено главное — влияет ли это на PPL/retrieval модели.** Это следующий эксперимент:
   встроить Fracode Memory в прямой проход и сравнить PPL и retrieval-accuracy с точной памятью.
4. Статистика modest: W=262K, 24 запроса. Нужно больше запросов и несколько сидов.
5. Не учтена стоимость обучения кодбука и кодирования на ingest (в результатах есть `fit_s`/`query_s`).
6. Кодбук обучался на той же матрице, которую кодирует — для честности нужно учить на held-out
   участке корпуса (иначе возможна подгонка под выбранный контекст).

## Следующий шаг

Встроить `FracodeMemory` в `chunked_forward`/`decode_step` как слой памяти и измерить
**PPL + retrieval** при 8×/16×/32× против точной памяти. Только это превращает «сжатие работает»
в «модель работает со сжатой памятью».
