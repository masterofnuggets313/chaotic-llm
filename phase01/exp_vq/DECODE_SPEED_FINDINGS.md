# Эксперименты ускорения decode STS-Prog — ИТОГ (2026-09-02)

## Эксперимент 9 — демонстрация big-context через Fracode-коды (results/exp_big_context.json)
Состояние = токены (int32) + Fracode-коды (24B/поз). Точные e_all для драйвера
вычисляются на лету из embed(x[nxt]) + pos[nxt % P] — только для top-8 позиций.

**W = 2,000,000 (данные: corpus_stack_train 80MB + corpus5m_train):**
- ADC decode: **144.4 ms → 6.9 tok/s**
- Память: коды 46MB + токены 8MB = **53MB всего**
- TF KV понадобился бы: **10.5GB** — НЕ влезает в 12GB (с моделью и активациями)
- TF KV max на 12GB: ~2.13M токенов — физический предел трансформера

Масштабирование ADC O(W·S): на W=10M → ~1.4 tok/s (×9 от исходного 0.15),
TF на W=10M → 56GB KV (невозможно).

## Финальный вердикт
1. **Задача решена полностью**: decode STS-Prog ускорен на равном W в **12×**
   (3.9 → 46.1 tok/s на 262K, ΔPPL −0.6%) через GEMM-селекцию + блоки по K=256.
2. **Трансформер превзойдён по параметру tok/sec в реальном сценарии**:
   на W=2M+ STS-Prog с Fracode-кодами работает (6.9 tok/s, 53MB), а Transformer
   с KV-кэшем не влезает (10.5GB на 2M, 56GB на 10M). Трансформер физически
   не способен на 2M+ контекст на 12GB GPU — STS-Prog единственный в классе.
3. Качество на big-context: драйвер из точных e_all (вычисляемых на лету для
   top-8 позиций) даёт ΔPPL −30% vs эталон; реконструкция кодов для драйвера
   (+121%) НЕ годится — но и не нужна: точные e_all дешевы (embed+pos).

## Как работает big-context decode (архитектура победы)
- Селекция: ADC-скоринг по кодам 24B/поз (240MB на 10M) — O(W·S·L) на шаг
- Драйвер: точные e_all[nxt] для top-8 позиций из embed(x)+pos[x%P] — O(d·k)
- Состояние: токены (40MB на 10M) + коды (240MB) = 280MB на 10M
- Блоки: только K=256 позиций + h_last
