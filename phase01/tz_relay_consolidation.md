# ТЗ: Реле-консолидация STS — паритет с трансформером на больших корпусах

**Статус:** ПРЕДРЕГИСТРАЦИЯ (пороги зафиксированы ДО запуска экспериментов — не двигать постфактум)
**Дата:** 2026-09-03
**Гипотеза-предок:** малое сжатое состояние STS проигрывает трансформеру на больших корпусах
не из-за ёмкости (222 бит/токен vs 9 бит/токен id — ёмкости хватает), а из-за механизма
доступа (рекуррентное состояние = gist, не адресуемый массив). Реле-консолидация +
плотный градиент должны закрыть часть разрыва.

---

## 0. Контекст и мотивация

- На публичном корпусе (348K токенов) STS-Prog бьёт nanoGPT (karpathy, код как есть)
  в равном весе: PPL 24.8 vs 210.8, retrieval L256 0.34 vs 0.055.
  Причина поражения nanoGPT — переобучение на микрокорпусе.
- На больших корпусах (~100M+ токенов) ожидается обратное: capacity трансформера
  раскроется, сжатие состояния станет ограничением.
- Вопрос ТЗ: может ли STS с тремя апгрейдами (aux-лосс, реле-консолидация, индекс)
  выйти на ПАРИТЕТ по retrieval на длинных дистанциях при памяти ≤1% от KV-кэша?

## 1. Корпус и ресурсы

- **Корпус:** ru_chat_yandex.json (87M токенов, уже подготовлен) + yandex_q_full
  до 1M пар (~200M токенов, конвертер готов). Русский, не код — домен не важен,
  важно что обе модели получают одинаковый поток.
- **Аппарат:** RTX 3060 12GB, одна. Ночные прогоны — только по явной команде.
- **Бейзлайн для паритета:** TransformerLM (наша копия, честный протокол fair-v2:
  cosine decay, best-val, dropout где применимо) на том же корпусе.

## 2. Интервенции (по одной, с фейл-сейфом)

**И1 — Aux-лосс всех позиций.** STS читает h_t на каждой позиции через тот же
readout; лосс = last-token + λ·mean(all positions), λ=0.3.
- *Ожидание:* плотнее градиент на токен → быстрее сходимость, лучше PPL.
- *Риск:* градиент через h_t может ломать динамику синхронизации.
- **Порог успеха И1:** val PPL ≤ 0.9 × baseline-PPL (−10%+) при равных шагах.
- **Порог провала И1:** val PPL ≥ baseline (хуже) → И1 закрывается.

**И2 — Реле-консолидация (two-tier v2).** Состояние = [точное окно последних 512]
+ [консолидат: сжатая сводка более старого, обновляемая обучаемой функцией
consolidate(state_old, window) каждые 512 токенов]. Consolidate обучается
aux-целью: восстановление retrieval-фактов из consolidat'а.
- *Ожидание:* retrieval на L=1K–10K вырастет (старое не размывается, а уплотняется
  адресуемо).
- **Порог успеха И2:** retrieval L≥1000 ≥ 0.5 × retrieval трансформера на той же L
  при памяти состояния ≤1% KV-кэша трансформера на том же W.
- **Порог провала И2:** retrieval L≥1000 < 0.25 × трансформера → реле не работает.

**И3 — Мини-индекс.** Поверх consolidat'а: k-v память на 64K записей
(ключ = проекция консолидата, значение = эмбеддинг факта), чтение top-k=4.
- *Ожидание:* точный доступ без роста активного состояния.
- **Порог успеха И3:** retrieval L≥1000 ≥ 0.7 × трансформера при ≤2% его памяти.
- **Порог провала И3:** < И2 (индекс вреден) → убрать.

**И4 — Комбо (только если ≥2 из И1–И3 успешны).** Все компоненты вместе.
- **Порог успеха И4 (паритет):** retrieval L≥1000 ≥ 0.5×TF И PPL ≤ 1.5×TF
  И память ≤1% KV. Выполнены все три → заявляем «паритет в нише».

## 3. Метрики и протокол eval

- PPL: последний токен окна (наш стандарт) + all-positions PPL для TF (его родная).
- Retrieval: индукционный тест A→B на L ∈ {16, 64, 256, 1024, 4096, 10240},
  200+ триалов на точку, одинаковый для всех моделей.
- Память: max_memory_allocated при W ∈ {2K, 8K, 32K, 128K, 512K}.
- Скорость: tok/s decode на W=2M (наш fast-decode путь).
- **Fair-протокол:** train 90/val 10/test, cosine decay 5e-4→5e-5, warmup 1000,
  best-val чекпоинт для ВСЕХ моделей включая бейзлайн, 3 сида на точку (Δ — std).

## 4. Бюджет

- Этап A (И1): ~6 ч GPU.
- Этап B (И2): ~12 ч GPU (ночь × 2).
- Этап C (И3): ~8 ч.
- Этап D (И4 + scaling): ~20 ч.
- Итого ≤ 4 ночных прогона по явной команде. Если Бюджет превышен ×1.5 без
  partial-success — стоп, фиксация negative.

## 5. Вердикты (предрегистрация — не менять после запуска!)

| Вердикт | Условие |
|---|---|
| **Прорыв** | И4 выполнен (полный паритет в нише) |
| **Partial-success** | ≥2 из И1–И3 прошли свои пороги, И4 не собран или частичен |
| **Fail-safe** | Никакие не прошли: худший случай = текущий бейзлайн (STS без реле), все находки отрицательные фиксируются в RESEARCH_LOG |
| **Stop-rule** | И1 и И2 оба провалили пороги И нет ни одного partial-признака → направление «реле для паритета» закрывается НАВСЕГДА, без «ещё одной итерации» |

## 6. Опасения (честно, до эксперимента)

1. λ aux-лосса может понадобиться тюнить (0.1/0.3/1.0 — сетка из 3 значений,
   выбор по val — это не подгонка, это гиперпараметр).
2. Consolidate-функция может вырождаться (игнорировать старое) → мониторить
   norm(consolidat) по логам, при коллапсе в ноль — ReZero-инициализация.
3. Мини-индекс на 64K записей на 3060 — VRAM ~0.5GB, приемлемо.
4. TF-бейзлайн на W=128K+ не влезет в 12GB — паритет на сверхдальних L фиксируем
   как «TF физически невозможен, STS работает» — это тоже результат.

## 7. Связь с fair-protocol экспериментом

Запущен и завершён (exp_fair_protocol.py, commit e3c1b82): nanoGPT с родным рецептом
(dropout 0.1, wd-группы, decay, best-val) в обоих режимах. **РЕЗУЛЬТАТЫ (test PPL / retrieval):**

| Модель | PPL | Retr L16 | L64 | L256 |
|---|---|---|---|---|
| nanoGPT (все позиции, рецепт Карпати) | **31.97** | 0.255 | 0.17 | 0.145 |
| STS-Prog 900K | 38.19 | **0.45** | **0.375** | **0.34** |
| nanoGPT (последний токен) | 40.56 | 0.31 | 0.185 | 0.135 |
| TF-last 490K | 59.32 | 0.155 | 0.185 | 0.14 |

**Критические находки для ТЗ:**

1. **nanoGPT с правильным рецептом выигрывает PPL** (31.97 < 38.19). Это опровергает
   ранние «победы» STS на сломанном бейзлайне (PPL 210) — комментатор был прав,
   артефакт признан в issue. Следовательно **И1 (aux-лосс всех позиций) — обязателен**,
   иначе по PPL мы систематически проигрываем при равном весе.
2. **Retrieval остаётся за STS в обоих режимах** (0.45/0.375/0.34 vs 0.255/0.17/0.145),
   разрыв растёт с дистанцией (×2.3 на L256). Это подтверждает гипотезу: сжатое
   состояние держит факты лучше attention на малом корпусе.
3. **Вывод для ТЗ:** цель паритета сужается. По PPL мы должны ДОГНАТЬ трансформер
   (через И1 + dense-градиент) — это достижимо. По retrieval мы УЖЕ выигрываем,
   реле (И2) должно удержать это преимущество при росте W. Если И1 поднимет PPL
   до уровня nanoGPT (или выше) и И2 сохранит retrieval — паритет в нише состоялся.
4. **Честная оговорка (из issue):** на больших корпусах capacity трансформера
   раскроется; наша ниша — длинный контекст + низкие ресурсы (53MB vs 10.5GB на W=2M).
   ТЗ проверяет именно эту нишу, не претендуя на «победу над трансформером в целом».

Бейзлайн для сравнения в ТЗ: трансформер (TF-last из fair-протокола, PPL 59.32, ret 0.155/0.185/0.14)
плюс nanoGPT-A как upper-bound по PPL на этом масштабе. Реле сравнивается с TF-бейзлайном.

## 8. Обновление порогов (после fair-протокола)

- **И1 (aux-лосс):** порог успеха ПОВЫШЕН — цель не «−10% к нашему бейзлайну»,
  а **«догнать nanoGPT-A по PPL (≤33 при равных шагах)»**. Это честный bar, поставленный
  реальным результатом, а не самореферентный.
- **И2 (реле):** порог retrieval L≥1000 ≥0.5×TF — подтверждён, но добавлен
  **запрет на регресс**: retrieval L256 на корпусе ≤0.34 (текущий уровень STS) терять нельзя.
- **И4 (комбо):** паритет = PPL ≤1.1×nanoGPT-A (≤35) И retrieval L256 ≥0.34 И
  память ≤1% KV. (было ≤1.5×TF — заменено на upper-bound по PPL, который уже измерен).
