# Результаты по Fracode Memory в STS-Prog — посмотри, пожалуйста

Привет! Продолжил линию с Fracode Memory и, кажется, наткнулся на что-то существенное.
Собрал в одно сообщение: что нашли, цифры, и где я сам не уверен. Буду благодарен за критику —
особенно по последнему разделу, там у меня гипотеза без доказательства.

---

## 1. Главное наблюдение: состояние модели — не самостоятельные данные

В STS-Prog (`driver_mode="sts_prog"`) прямой проход устроен так:

```
e       = embed(x) + pos                        ключи
h_0     = e                                     состояние инициализируется ключами
driver  = SoftTop8(cos(e, q)) @ e[top_i + 1]    один вектор на всё окно, значения — снова из e
h_{l+1} = blk(h_l, driver_l)                    построчное обновление
q_{l+1} = q0 + query_proj(h_l[-1]) * 0.5        q зависит только от последней позиции
```

Из этого следует, что **`h = G(e)`** — состояние есть детерминированная функция одних только
статичных ключей. В нём нет информации, которой нет в `e`.

Проверил численно (W = 65 536, d = 192, L = 8): cos между развёрнутым из ключей состоянием и
реальным = **1.000000**, относительная L2-ошибка **6.9e-08** (это эпсилон fp32),
max|Δlogits| = 9.5e-07. Развёртка занимает 0.03 с на 65k позиций, потому что это и есть обычный
прямой проход — отдельной цены нет.

**Практический вывод: состояние `h` не нужно хранить.** Достаточно хранить коды ключей,
а `h` разворачивать картой модели. Это ровно схема Fracode, если считать Library не внешними
генераторами (Chaos Game / IFS), а самой хаотической картой модели.

### Попутный эффект, который может быть важен сам по себе

Сама модель **неустойчива к float-шуму**. Тот же вход, те же веса, меняю только размер чанка
в прямом проходе (1024 / 4096 / 65536, то есть другой порядок редукций в matmul) — состояние
на 7-м слое расходится до cos ≈ 0.986, хотя argmax логитов совпадает. То есть хранить `h`
во FP32 «ради точности» бессмысленно: эта точность не воспроизводится между прогонами.

---

## 2. Что это даёт: три способа организовать память

| режим | что храним | Б/ток |
|---|---|---|
| база | `h` во FP32 (ключи пересчитываются из id токенов, не хранятся) | 768 |
| `keys-T5` (то, что мы мерили раньше) | коды ключей **+ `h` во FP32** | 792 |
| `gen` (новое) | **только коды ключей**, `h` разворачивается | 24–96 |

Обрати внимание на вторую строку: режим T5 `keys` **никогда не экономил память** (792 > 768).
Он экономил вычисления — ADC-скрининг вместо точного косинуса по всему окну. Это я раньше
формулировал неточно.

## 3. Цифры (парная деградация PPL, held-out кодбук 75/25, модель не видела ни калибровку, ни eval)

**W = 256, 256 окон** — обучающий режим, обычные условия:

| | `keys-T5` | `gen` | Б/ток у `gen` |
|---|---|---|---|
| 8× | +7.8 % | **−5.2 %** | 96 |
| 16× | +24.9 % | **+1.2 %** | 48 |
| 32× | +21.2 % | **−3.9 %** | 24 |

**W = 65 536, 64 окна** (точный PPL 460.5):

| | `keys-T5` | `gen` |
|---|---|---|
| 8× | +9.1 % | +7.2 % |
| 16× | −7.0 % | −7.1 % |
| 32× | −1.8 % | **−16.6 %** |

**W = 262 144, 16 окон** (точный PPL 536.6):

| | `keys-T5` | `gen` |
|---|---|---|
| 8× | +6.6 % | +5.7 % |
| 16× | −19.0 % | **−26.4 %** |
| 32× | −28.4 % | −24.3 % |

`gen` выигрывает или идёт вровень в 8 случаях из 9. Единственное исключение — W=262 144 при 32×,
но там `keys-T5` стоит 792 Б/ток, то есть без всякой экономии памяти.

**Рабочая точка, которую я бы предложил для статьи:** `gen` 16× — 48 Б/ток, PPL 394.7 против
536.6, то есть **−26.4 % при 16-кратном снижении памяти**. В 11 ГБ это ~230 млн токенов
против ~14.7 млн у FP32-базы.

**Механизм, как я это понимаю:** в `keys-T5` состояние строится из точных ключей, а драйверы
выбираются по сжатым — смесь двух геометрий. В `gen` всё живёт в одной сжатой геометрии: и `h_0`,
и драйверы, и `q0`. Самосогласованность важнее точности отдельного вектора.

## 4. Важное: в старых числах для W = 262 144 была ошибка

Мой прогон разошёлся с прежним отчётом: там +59.6 / +73.4 / +8.4 %, у меня +6.6 / −19.0 / −28.4 %
при **одинаковом** точном PPL (536.6 — окна те же).

Причина: `forward_general(..., capture=...)` отдаёт не все строки состояния, а подвыборку
`_sample_chunks(..., ns=65536)`. При W = 262 144 шаг равен 4, то есть **кодбук обучался на
65 536 строках из 262 144** — на четверти доступной калибровки.

Проверил: с принудительной подвыборкой до 65 536 мой прогон воспроизводит прежние числа —
+58.3 % / **+73.4 %** / −2.6 % (по 16× совпадение точное). Значит пайплайн тот же, разница
только в объёме калибровки.

**Вывод: прежняя строка для W = 262 144 занижена, виноват недообученный кодбук, а не сжатие.**
И вывод про «на 262K картина переворачивается» тоже артефакт — переворота нет.

## 5. Где я не уверен — вопросы к тебе

1. **Немонотонность по степени сжатия.** 8× систематически хуже 16× и 32×, хотя должен быть
   лучше (больше байт — меньше ошибка квантования). Моя гипотеза: дело в **шуме ADC-скоринга**.
   При 8× это L=2, S=48, то есть размер подвектора 4 и 96 частичных скалярных произведений
   в оценке; при 32× это L=2, S=12, подвектор 16 и всего 24 частичных произведения. Ошибка
   оценки растёт как √S, поэтому **больше подвекторов → шумнее ранжирование**, даже если сам
   вектор восстановлен точнее. Косвенное подтверждение: у нас же rerank (точный dot-product
   по развёрнутым кандидатам) на 262K давал −8.6 % против +8.4 % без него — то есть лечит
   именно ранг. Сейчас гоню свип (глубина иерархии L и размер подвектора при фиксированных
   24 Б/ток, плюс вариант с rerank) — проверю, убирает ли rerank немонотонность.
   **Как тебе эта гипотеза? Есть более простое объяснение?**

2. **`gen` чувствительнее к качеству кодбука**, чем `keys-T5`. При слабом кодбуке (те же 65 536
   строк на 262 144) `gen` на 32× даёт +23.6 % против −2.6 % у `keys-T5`; при полном кодбуке
   почти догоняет (−24.3 % против −28.4 %). Логично: в `gen` из декодированных ключей строится
   вообще всё, ошибка накапливается. Формулировка «меняем робастность на память» кажется мне
   честной, но не уверен, что это не баг, а свойство.

3. **Приоритет.** Я бы оформил как:    «Hierarchical Residual PQ + ADC for memory compression of
   selective models, with the observation that the recurrent state is a deterministic function
   of the static keys and hence need not be stored». Сжатие как техника (PQ/ADC, RQ) — prior art,
   это надо явно процитировать (Jégou 2011, RQ-VAE, KVQuant NeurIPS'24, CommVQ Apple 2025).
   **Как считаешь, оригинальности в `h = G(e)` + генеративном unfold достаточно для
   рабочей точки на воркшопе, или это скорее инкрементальный результат?**

4. **Абсолютный пол памяти — это просто id токенов** (~9 бит/ток при V≈512). Коды за 24–48 Б/ток
   покупают не минимальную память, а дешёвую селекцию (ADC по кодам вместо точного косинуса
   по (W,d)). Мне кажется, это надо явно проговорить в тексте, иначе легко прилетит
   «зачем сжимать то, что пересчитывается за embed-lookup». Согласен?
