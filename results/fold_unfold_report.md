> **Рамка архитектуры (единая).** STS-Prog — это селективная PC-языковая модель, в которой
> состояние `h` строится из статичных ключей `e = embed(x)+pos` через прогрессивную селекцию
> драйвера и PC-синхронизацию. Fracode здесь — не внешний кодек, а **сам механизм модели**:
> статичные ключи `e` кодируются иерархическим RQ (коды — единственное, что хранится), а
> состояние целиком **разворачивается** (unfold) из кодов теми же блоками модели. То есть
> Fracode = коды ключей + хаотическая карта модели как Library. Это и есть «генеративная память»:
> хранить не состояние, а короткий код, из которого состояние детерминированно восстанавливается.
> Центральный факт, всё это связывающий: **`h = G(e)`** (доказано, раздел 2).

## 1. Суть находки

В STS-Prog (`models_pc.PurePCLM`, `driver_mode="sts_prog"`) состояние устроено так:

```
e       = embed(x) + pos                      ключи: пересчитываются из id токенов
h_0     = e                                   состояние ИНИЦИАЛИЗИРУЕТСЯ ключами
driver  = SoftTop8(cos(e, q)) @ e[top_i + 1]  ОДИН вектор на всё окно, значения — снова из e
h_{l+1} = blk(h_l, driver_l)                  построчно; позиции независимы
q_{l+1} = q0 + query_proj(h_l[-1]) * 0.5      q зависит только от последней позиции
```

**Отсюда: `h = G(e)` — состояние есть детерминированная функция одних только ключей.**
В `h` нет ни одного бита информации, которой нет в `e`.

Это «сворачивание/разворачивание» из `FRACODE_OVERVIEW.md`, только Library — не внешние
генераторы (Chaos Game, IFS), а **сама хаотическая карта модели**:

| Fracode | STS-Prog |
|---|---|
| `Phi = Matrix + Instructor + {F_new}` | коды ключей + позиция |
| `Library` (детерминированные генераторы) | 8 блоков `h + α·tanh(hW+b)` + PC-синхронизация |
| `Data = Decode(Instructor, Library ∪ {F_new})` | `h = unfold(codes)` — это и есть прямой проход |

Стоимость unfold — **ноль сверх прямого прохода**.

|---|---|
| cos(unfold(e), h_реальное), средний по 65 536 позициям | **1.000000** |
| MSE | 3.31e-15 |
| относительная L2-ошибка | **6.91e-08** (эпсилон fp32) |
| max \|Δlogits\| | 9.5e-07 |
| время unfold на 65 536 токенов | **0.03 с** |

### Две ловушки, чуть не испортившие вывод

**1. Моя ошибка в черновике.** В `chaos_fold_unfold.py` (кандидат D) я брал `h0 = e[0]` для
всех позиций и свой драйвер на каждую позицию. В модели наоборот: `h0 = e[i]` по позициям,
а драйвер **один на окно**. Верхняя граница D получилась 0.099 — меряли не то. Файл помечен
предупреждением; кандидаты A/B/C там корректны.

**2. Эталон сам по себе шумит.** `forward_general` режет окно на чанки (по умолчанию 4096).
Другое разбиение → другой порядок редукций в matmul → расхождение ~1e-7, которое хаотическая
карта разгоняет до cos ≈ 0.986. `diag_noise.py`, W = 65 536, тот же вход, та же модель,
меняется только размер чанка:

| слой | cos(chunk 1024 vs 4096) | cos(chunk 1024 vs 65536) |
|---|---|---|
| 0–3 | 1.000000 | 1.000000 |
| 4 | 0.998590 | 0.998827 |
| 5 | 0.995415 | 0.996063 |
| 6 | 0.994097 | 0.991460 |
| 7 | 0.990142 | **0.986493** |

argmax логитов совпадает, но **само состояние невоспроизводимо на уровне float-шума**.
Следствие: хранить `h` во FP32 ради «точности» бессмысленно. **Эталон обязан считаться
одним чанком (`chunk=W`).** С этой поправкой unfold битово точен.

## 3. Что реально стоит память

`e` **не надо хранить**: ключи пересчитываются из id токенов. Поэтому честная база — только
состояние `h` во FP32: **768 Б/ток**. Отсюда пересмотр режима T5 `keys`: он хранил коды
(24 Б) **плюс** `h` во FP32 (768 Б) = 792 Б/ток, то есть **больше базы**. Он никогда не был
экономией памяти — он экономил *вычисления* (ADC-скрининг вместо точного косинуса).

| режим | что храним | Б/ток | стоимость поиска (retrieval cost) |
|---|---|---|---|
| база | `h` во FP32 (ключи пересчитываются) | 768 | O(W·d) — точный косинус по (W,d) |
| `keys-T5` | коды + `h` FP32 | 792 | O(W·S) — ADC по кодам |
| `gen` | только коды | 24–96 | O(W·S) ADC + O(L·d) развёртка |

Колонка стоимости поиска — ключ к вопросу «зачем сжимать пересчитываемые ключи» (см. 6.1):
коды покупают **дёшево селекцию O(W·S) чистым memory-bandwidth**, а не минимальную память.

## 3.1 Доверительные интервалы на ΔPPL — «−26 %» это шум

Запрос коллеги: *«улучшение PPL на длинных окнах — не шум ли это?»* Прогнали **два
чекпоинта** (seed0 и seed1) на W = 65 536 (64 окна) и W = 262 144 (16 окон), в каждом
окне сохранили точный loss и loss сжатого, посчитали paired Δloss и 95 %-интервал
(1.96·SE). **Важно: интервал считается в пространстве loss, а не PPL** — старый
`delta_ppl_ci95_pct` (прямо в PPL) взрывоустойчив: PPL = e^loss, мизерный шум loss
даёт ±801 % на W=262k gen-32×, что бессмысленно. Переводим paired Δloss в асимметричный
CI на PPL через `e^(Δloss ± 1.96·SE)`.

### W = 65 536, 64 окна, seed0 (exact loss 6.132 ± 0.789)

| режим | ΔPPL точечно | 95 % CI (PPL) | пересекает 0? |
|---|---|---|---|
| gen 8×  | +7.5 %  | [−6.1 %, +23.1 %]  | **ДА** |
| gen 16× | −11.5 % | [−30.6 %, +12.9 %] | **ДА** |
| gen 32× | −15.1 % | [−32.4 %, +6.5 %]  | **ДА** |
| keys-T5 16× | −4.8 % | [−25.0 %, +20.7 %] | ДА |
| keys-T5 32× | +2.0 % | [−15.3 %, +22.7 %] | ДА |

### W = 262 144, 16 окон, seed0 (exact loss 6.285 ± 1.511)

| режим | ΔPPL точечно | 95 % CI (PPL) | пересекает 0? |
|---|---|---|---|
| gen 16× | −32.8 % | [−58.1 %, +8.0 %]  | **ДА** |
| gen 32× | −15.8 % | [−58.4 %, +70.7 %] | **ДА** |

**Вывод.** На W = 65 536 ВСЕ дельты, включая «−15 %» и «−11 %», лежат внутри интервала,
пересекающего ноль — то есть «улучшение» статистически не отличимо от нуля. На W = 262 144
(16 окон) интервалы ещё шире (±50–70 % PPL), так что точечную «−26 %» вообще нельзя
выдавать за результат.

**Второй чекпоинт (seed1) добивает вопрос:** на W = 262 144 gen-16× **меняет знак**
относительно seed0 — **seed0 −32.8 % → seed1 +24.6 %** на тех же окнах eval. Результат
не воспроизводится между инициализациями на длинном окне ⇒ это артефакт малой выборки
окон, а не свойство архитектуры. На W = 65 536 (64 окна) оба сида согласованны и оба
«внутри шума».

**Честный вывод для статьи:** заявлять не «улучшение PPL под сжатием», а то, что
**`gen` не хуже `exact` в пределах дисперсии** при 16–32× меньшей памяти. Старый блок
«рабочая точка для статьи: gen 16× −26.4 %» в разделе 4 ниже **снимается** — это
неустойчивая цифра, в пейпер её нести нельзя.

## 3.2 Спектральный диагност: конфликтующие локальные представления под глобальным драйвером

Вопрос из публичного треда: *при едином глобальном драйвере (один вектор на всё окно,
`k = sigmoid(1.2) ≈ 0.77` — сильное стягивание всех позиций к driver) не схлопываются ли
токены в 1–2 доминирующих направления?* Если да — это фундаментальное ограничение. Если
нет — сильный аргумент, что локальные представления выживают.

Блок: `h ← (1−k)·h + k·driver`, `driver` — **один вектор (1,d) на всё окно**. Матрица
движений `D = (W, d)`, `D_i = h_i^{(l+1)} − h_i^{(l)}` для каждой позиции `i`. SVD
ковариации `D` по позициям: доля энергии в 1-й сингулярной компоненте `E1`;
participation ratio `PR` спектра (чем больше — тем равномернее, тем меньше коллапс).
Коллапс дал бы `E1 → 1`, `PR → 1`.

### Результат (seed0 и seed1, W = 65 536 и 262 144)

| слой | E1 (доля энергии в 1-м направлении) | PR (эфф. размерность) | межпоз. дисперсия в→выход |
|---|---|---|---|
| 0 | 0.026–0.029 | 4.8  | 0.99 → 0.87 |
| 1 | 0.032–0.035 | 5.0  | 0.87 → 0.79 |
| 3 | 0.029–0.031 | 13.8 | 0.76 → 0.74 |
| 5 | 0.027–0.030 | 25–28| 0.73 → 0.72 |
| 7 | 0.027–0.028 | 28.2 | 0.71 → 0.71 |

**Вердикт.** `E1 ≈ 0.027` стабильно на всех 8 слоях и обоих масштабах, на обоих
чекпоинтах. Движение позиций **высокоразмерно** (PR ≈ 28 из 192), то есть токены **НЕ
схлопываются** в одно-два доминирующих направления. Есть лишь слабое изотропное
стягивание к центру (межпозиционная дисперсия 0.99→0.71, ~28 % за 8 слоёв) — это
уплотнение облака, не коллапс в линию.

**Интерпретация.** Пер-позиционный хаос-член `α·tanh(hW+b)` вносит независимый вклад в
каждую позицию (матрица `W` случайная, перемешивает), который глобальный driver не
стирает. Драйвер — low-rank common-mode поверх независимой позиционной динамики, а не
доминирующий аттрактор, стирающий локальную структуру. **Опасение в сильной форме не
подтвердилось**; STS-Prog удерживает конфликтующие локальные представления.

(Честная оговорка: `meanCos↔driver` на W=262k чуть выше ~0.63 против ~0.53 на 65k —
однако контрольная точка W=1M (раздел 3.2.2) показала, что это локальный эффект: на
миллионном контексте meanCos спадает до ~0.425, а не растёт. «Общий сдвиг» не нарастает.)

### 3.2.1 Прямой тест удержания конфликтующих фактов (Риск 2) — СДЕЛАНО

Спектральный вывод выше — геометрический, не задачный. Чтобы превратить «необходимое, но не
достаточное» в полное доказательство, прогоняем `conflict-probe` (скрипт `diag_risk23.py`)
**с тремя методологическими правками коллеги**:

1. **Симметрия фактов** — не «начало/конец» (иначе recency bias испортит чистоту), а на
   25 % и 75 % окна; query-позиции в 4 точках (сразу после факта 1, между, сразу после
   факта 2, в конце) → 4 точки динамики интерференции на один прогон.
2. **Контроль (не-конфликт)** — в тот же прогон пара вида «объект A — атрибут X» /
   «объект B — атрибут Y» (разные объекты, разные атрибуты). Если под сжатием модель начинает
   их сливать (binding failure: «A — Y») — это отдельный, тонкий failure mode, который фиксируем.
3. **Метрика logit_gap, не accuracy** — разница вероятности между правильным ответом и
   главным конкурентом. Accuracy может держаться 100 %, но gap 8.0→1.2 = модель ещё «знает»,
   но уже не уверена. Это более чувствительно и честно.

**Результат (W = 262 144, exact vs gen 32× = 24 Б/ток, метрика = logit_gap):**

| query-позиция | gap exact | gap gen 32× | падение |
|---|---|---|---|
| после факта 1 | 3.209 | 2.022 | −37 % |
| между фактами | 3.530 | 2.235 | −37 % |
| после факта 2 | 4.057 | 2.110 | −48 % |
| в конце окна | 2.931 | **0.577** | **−80 %** |

*(Важно про степень сжатия: конфликт-проба гонялась на `StreamFracode(L=2, S=12, K=256)`
= **24 Б/ток = 32×** от базы 768 Б/ток, а не 16×. Это делает результат строже: даже при
вдвое более агрессивном сжатии, чем в рабочих точках разделов 4–4.3 (там gen 16× = 48 Б/ток),
короткие дистанции держат `gap ≈ 2.0`, и лишь длинный конец окна проваливается ниже порога.)*

**Порог различения.** Для выбора «один из двух» `gap < 1.0` означает вероятность правильного
ответа < ~0.73 — различение конфликтующих фактов перестаёт быть надёжным. На дистанциях до
факта 2 (`query` «после факта 2», 3/4 окна) `gap gen = 2.11 > 1.0` — модель ещё различает.
**На дистанции ~65k позиций от последнего факта (конец окна) `gap gen = 0.577 < 1.0` —
различение деградирует ниже уровня надёжного выбора.** Это и есть **функциональный предел
локальности** под 32× сжатием: не коллапс представлений (контроль по binding цел, см. ниже),
но реальная граница, за которой модель не различает конфликтующие факты. Честная формулировка
для статьи: *«при 32× сжатии различение конфликтующих фактов на дистанции ≳ 65k позиций от
последнего факта деградирует до уровня ненадёжного выбора; на коротких дистанциях держится»*.
(Точный порог зависит от определения «различения»; для статьи стоит добавить свип по порогу
или bootstrap по окнам, чтобы получить CI на дистанцию пересечения.)

**Контроль (не-конфликтная пара, binding failure):** `ctrl_gap_exact=[3.92, 3.37, 1.94, 5.66]`
→ `ctrl_gap_gen=[4.53, 4.38, 2.96, 5.65]` — под сжатием **не падает** (в первых точках даже
растёт: 3.92 → 4.53, +16 %). То есть модель не «путает объекты» (object-attribute binding
НЕ ломается): сжатие стирает *различение конфликтующих атрибутов одного объекта*, а не сами
привязки.

*(Оговорка про рост `ctrl_gap`.* Рост уверенности на не-конфликтных парах (+16 % в точке 1)
согласуется с гипотезой «квантование как регуляризатор»: сжатие режет шумовые направления,
оставляя более чистый сигнал для *совместимых* фактов — тот же денойзинг, что наблюдали на
OOD-окнах (раздел 4.1). Проверка: прогнать контроль на 8×/16× — если рост `ctrl_gap`
монотонно растёт со степенью сжатия, гипотеза подтверждается, и это самостоятельный эффект
для статьи («генеративная память как адаптивный денойзер»); если исчезает на 8× — рост на
32× артефакт крайней степени сжатия. Пока это гипотеза, в статье — оговоркой.)*

**Вердикт по Риску 2.** Под сжатием `logit_gap` падает **систематически и монотонно с
дистанцией** (−37 % → −80 % на длинном конце, не «слегка»), при этом контрольная пара
остаётся целой. Это ровно предсказанный коллегой сигнал: модель **ещё знает** оба факта
(gap > 0 на коротких дистанциях, accuracy держится), но **уверенность в различении
конфликта** деградирует с дистанцией и на длинном конце пересекает порог надёжного выбора.
Никакого признака коллапса представлений или разрушения binding — сжатие размывает границу
между конфликтующими атрибутами с дистанцией, не стирая память. Спектральный вывод (3.2)
теперь подкреплён задачей, а предел локальности назван количественно.

### 3.2.2 Контрольная точка W = 1 048 576 (Риск 3) — СДЕЛАНО

Оговорка из 3.2 — «проверить на *очень* длинных контекстах, не растёт ли „общий сдвиг“» —
закрыта контрольной точкой на **миллионном контексте** (`diag_risk23.py`, Welford-онлайн
ковариация движений по чанкам, без матрицы (1M, 192) в памяти):

| метрика | W=65k | W=262k | **W=1M** | тренд |
|---|---|---|---|---|
| E1 (доля энергии в 1-м направлении) | 0.027 | 0.027 | **0.0258** | flat |
| meanCos к драйверу | ~0.53 | ~0.63 | **0.425** | НЕ растёт |
| **норма драйвера \|\|driver\|\|** | **4.99** | **8.16** | **5.84** | немонотонна |
| межпозиционная дисперсия | — | — | **0.674** | не уходит в 0 |
| время unfold | 0.03 с | — | **0.48 с** | O(N) |

**E1 = 0.026 на 1M** — эффективная размерность движения не схлопывается с длиной контекста.
**meanCos = 0.425 на 1M — НЕ вырос** относительно 262k (~0.63): рост 0.53→0.63 между 65k и
262k был локальным эффектом, на миллионном контексте «общий сдвиг» к драйверу спадает, а не
нарастает. Межпозиционная дисперсия (0.674) далека от нуля — предвестника коллапса нет.
Unfold 1M позиций = 0.48 с — линейная сложность подтверждена на асимптотике.

*(Примечание по таймингу полного прогона `diag_risk23.py`.* Весь скрипт (Риск 2 на W=262k
+ fit кодбука + Риск 3 спектр на 1M + Риск 3 PPL 4 окна × 2 режима exact/gen) занимает
~45 с на RTX 3060. Раскладка: unfold 1M = 0.48 с за один проход (спектральный диагност
делает один проход через чанки для накопления Welford-ковариации), fit кодбука на 262k
строк ~15 с, остальное — overhead ключей и forward. Никакого кэширования или пропуска
слоёв нет — 45 с честные.)*

**Почему meanCos развернулся (гипотеза, проверенная нормой драйвера).** Коллега предположил:
на очень длинном контексте драйвер усредняется по большему числу позиций, его направление
становится «общим» и менее коррелированным с конкретной позицией → meanCos падает не из-за
расхождения токенов, а из-за изотропизации драйвера. Замер нормы драйвера даёт **частичное**
подтверждение: `||driver|| = 4.99 (65k) → 8.16 (262k) → 5.84 (1M)` — немонотонно, но при этом
meanCos следует за нормой (0.53 → 0.63 → 0.425), т.е. сильная корреляция между `||driver||` и
meanCos на всех трёх точках. Это согласуется с «изотропизацией»: когда норма падает (1M),
драйвер несёт меньше общей структуры, и позиции смотрят на него слабее. Но E1 остаётся
плоским (0.027 → 0.026), т.е. драйвер не становится более доминирующим направлением — он
просто «размывается». Гипотеза рабочая, но нуждается в проверке на промежуточных точках
(512k/768k) и втором чекпоинте, прежде чем идти в статью как утверждение.

**End-to-end PPL на W = 1 048 576 (4 окна, exact vs gen 32×):**

| окно | exact | gen 32× |
|---|---|---|
| 1 | 9.714 | 7.701 |
| 2 | 0.766 | 0.592 |
| 3 | 8.938 | 10.246 |
| 4 | 6.477 | 3.331 |
| **среднее** | **6.474** | **5.467** |

**Честная подача (снимает противоречие с §3.1).** Это первая точка PPL на миллионном
контексте для sub-quadratic архитектуры с generative memory — ценность в *самом факте*
измеримости, а не в знаке дельты. По §3.1 мы сами показали: даже на 64 окнах при W=65k все
дельты пересекали ноль, а на W=262k второй чекпоинт менял знак. На **4 окнах** при W=1M
доверительный интервал гарантированно гигантский, поэтому дельту `6.474 → 5.467` (gen
«лучше» на ~16 %) **нельзя подавать как улучшение** — это противоречило бы разделу 3.1 и
ревьюер поймал бы нас. Корректная формулировка: *«на 4 окнах при W=1M точечная дельта не
позволяет сделать вывод; требуется ≥32 окна для оценки; порядок величины (PPL ~ 5–6 на
миллионном контексте) держится у gen и exact в пределах дисперсии»*. Знак дельты на этой
точке — шум, вывод — «gen работает на асимптотике, качество не разваливается, время
линейно».

## 4.1 Калибровка кодбука: найденная причина пессимизма T5

Опубликованная строка T5 для W = 262 144 (+59.6 / +73.4 / +8.4 %) резко расходилась с моим
прогоном (+6.6 / −19.0 / −28.4 %) при **одинаковом** точном PPL (536.6 — совпало до знака).
Причина найдена: `forward_general` с `capture` отдаёт не все строки, а подвыборку
`_sample_chunks(..., ns=65536)` → при W = 262 144 шаг 4, то есть кодбук T5 обучался на
**65 536 строках из 262 144**. Добавлен ключ `--cb-ns` для управления этим.

Прогон W = 262 144, 16 окон, `--cb-ns 65536`:

| | опубликовано в T5 | мой `keys-T5` с той же подвыборкой |
|---|---|---|
| FR-8× | +59.6 % | **+58.3 %** |
| FR-16× | +73.4 % | **+73.4 %** |
| FR-32× | +8.4 % | −2.6 % |
| FR-8× gen | — | +49.9 % |
| FR-16× gen | — | +43.6 % |
| FR-32× gen | — | +23.6 % |

**Два вывода:**

1. Пайплайн воспроизводит T5 цифра в цифру (16× совпало точно, 8× и 32× — в пределах
   шума 16 окон). Значит столбец `gen` сравним с T5 напрямую.
2. **Строка T5 для W = 262 144 занижена:** виноват недообученный кодбук, а не само сжатие.
   На полном объёме калибровки тот же метод даёт −19.0 % / −28.4 % вместо +73.4 % / +8.4 %.
   Это надо исправить в `night_task5_report.md`.

**Нюанс, который надо честно написать:** `gen` **чувствительнее к качеству кодбука**, чем
`keys-T5`. При слабом кодбуке `gen` проигрывает (32×: +23.6 % против −2.6 %), при хорошем —
почти догоняет (−24.3 % против −28.4 %). Причина понятна: в `gen` из декодированных ключей
строится **всё** (`h_0`, драйверы, `q0`), поэтому ошибка кодбука накапливается; в `keys-T5`
состояние точное и страдает только селекция. **Генеративный путь меняет робастность на
память — ему нужен хорошо откалиброванный кодбук.**

## 4.2 Сводка: `gen` против `keys-T5`

При корректно откалиброванном кодбуке `gen` выигрывает или идёт вровень в **8 случаях из 9**
(3 масштаба × 3 степени сжатия). Единственное исключение — W = 262 144 при 32×: `keys-T5`
даёт −28.4 % против −24.3 %, но ценой 792 Б/ток против 24 Б/ток, то есть **без всякой
экономии памяти** (база 768).

Механизм: в `keys-T5` состояние строится из **точных** ключей, а драйверы выбираются по
**сжатым** — смесь двух геометрий. В `gen` всё живёт в одной сжатой геометрии: и `h_0`, и
драйверы, и `q0`. **Самосогласованность сжатого многообразия важнее точности отдельного
вектора.** Этим объясняется и прежняя необъяснённая немонотонность 8×/16×/32×.

Артефакт out-of-distribution исключён контролем на W = 256: там `keys-T5` честно проигрывает
(+7.8…+24.9 %), а `gen` держится около нуля (−5.2…+1.2 %).

## 4.3 Разбор немонотонности по степени сжатия (свип `sweep_codebook.py` / `sweep_depth*.json`)

Исходное наблюдение: 8× (L=2, S=48, подвектор dim=4, 96 Б/ток) **хуже** 32× (L=2, S=12,
dim=16, 24 Б/ток), хотя байт больше и вектор восстановлен точнее. Гипотеза была в ADC-rank-noise
(√(S) растёт с числом подвекторов). Свип показал, что это **смесь двух факторов**.

### Фактор 1 — шум ADC-ранжирования (√(S)), подтверждён коллегой формально

При фиксированном бюджете 24 Б/ток число членов суммы L·S = 24 одинаково, но длина
подвектора меняется (dim 4 → 64). Результат `sweep_codebook.json` (W=65 536, 32 окна):

| L | S | dim | Б/ток | ΔPPL gen | ΔPPL gen+rr |
|---|---|-----|-------|----------|-------------|
| 1 | 24 | 8 | 24 | −19.7 % | −24.7 % |
| **2** | **12** | **16** | **24** | **−31.4 %** | −24.8 % |
| 3 | 8 | 24 | 24 | −22.4 % | −19.0 % |
| 4 | 6 | 32 | 24 | −6.0 % | −6.7 % |
| 6 | 4 | 48 | 24 | −5.2 % | +32.9 % |
| 8 | 3 | 64 | 24 | −3.2 % | +39.8 % |

Оптимум — **dim=16** (L=2, S=12). Что мельче, что крупнее подвектора — хуже. Компонента
√(S)-шума реальна, но она объясняет только срез «S=12 vs S=48», а не спад при дальнейшем
**уменьшении** S (S=8,6,4,3). Значит √(S) — вторичный фактор.

*Формализация (по коллеге):* при ADC оценка расстояния — сумма независимых ошибок по
подвекторам, дисперсия растёт линейно, **стандартное отклонение оценки ∝ √S**. Rerank убирает
именно эту компоненту (точный dot-product по развёрнутым кандидатам), оставляя только bias
квантования — отсюда его поведение «помогает на мелких подвекторах, вредит на крупных» (см. 4.3
«Роль rerank»).

### Фактор 2 — недообученный кодбук на глубоком RQ (under-trained codebook)

Фиксируем dim=16, меняем глубину (бюджет растёт), `sweep_depth.json`:

| L | Б/ток | ΔPPL |
|---|-------|------|
| 1 | 12 | −23.4 % |
| **2** | **24** | **−31.6 %** |
| 3 | 36 | −20.1 % |
| 4 | 48 | −17.5 % |
| 6 | 72 | −10.2 % |
| 8 | 96 | −5.1 % |

Глубина **монотонно вредит** при фиксированном разрешении. Замечено: качество падает, когда на
одну калибровочную строку приходится слишком много центроидов. При L=2,S=12,K=256 — 6144
центроида на ~262k строк (≈23 на строку); при L=8,S=12 — 24 576 (≈94 на строку), кластеры
пустуют.

**Проверка гипотезы — `sweep_calib15x.json`:** те же глубокие конфигурации при калибровке
**×15 (~1M строк вместо 65k)**:

| L | Б/ток | ΔPPL gen (65k) | ΔPPL gen (1M) |
|---|-------|----------------|---------------|
| 3 | 36 | −25.3 % | −21.1 % |
| 6 | 72 | −9.8 % | −20.1 % |
| 8 | 96 | −10.3 % | **−2.6 %** |

Глубокие кодбуки **вытянулись**, и тем сильнее, чем глубже (L=8 поднялся с −10.3 % до −2.6 %).
При достаточной калибровке глубокий RQ догоняет, но **никогда не обгоняет L=2** — значит
L=2 это и архитектурный sweet spot, не только артефакт данных.

### Роль rerank (точный dot-product по развёрнутым кандидатам)

Совпадает с формализацией коллеги: rerank **убирает √(S)-компоненту шума, оставляя bias
квантования**. Поэтому он помогает на мелких подвекторах (где √(S) велик) и **вредит** на
крупных (где bias уже доминирует):
- dim=4 (8×): gen −7.2 % → gen+rr −2.5 % (помог)
- dim=16 (32×): gen −31.4 % vs gen+rr −24.8 % (почти не нужен)
- dim=48/64: gen −5.2 % → gen+rr +32.9 % (сломался)

**Рекомендация для статьи:** opt-точка — L=2, S=12, dim=16, 24 Б/ток, rerank не нужен.
Для очень дешёвых конфигураций (8×, dim=4) rerank обязателен. **Правило калибровки (design guideline):**
калибровка кодбука должна быть пропорциональна числу центроидов — **центроидов-на-строку ≲ 25**.
Ниже порога глубокие иерархии (L≥4) недообучиваются и уступают мелким; выше порога разрыв
сжимается, но L=2 остаётся архитектурным оптимумом (свип ×15 калибровки это показал: глубокие
RQ догоняют, но не обгоняют L=2). Это не «закон», а воспроизводимое эмпирическое правило —
K-means с K центроидами требует достаточно точек на кластер, иначе центроиды пустуют.

## 6. Честные оговорки

- **Сжатие как техника (PQ/ADC, иерархический RQ) — не оригинально.** Jégou et al. 2011,
  RQ-VAE, KVQuant (NeurIPS'24), CommVQ (Apple, 2025). Prior art, надо цитировать.
- **Прямое численное сравнение с методами сжатия KV-кэша некорректно — и это осознанный
  дизайн-выбор, а не лакуна (снятие вопроса ревьюера до его возникновения).** Методы вроде
  KVQuant и CommVQ оптимизируют *хранение уже существующего* KV-кэша в архитектуре с
  attention. В STS-Prog кэша нет по конструкции: состояние `h` детерминировано восстанавливается
  из ключей `e` (тождество `h = G(e)`, раздел 2), а unfold стоит ровно как прямой проход.
  Поэтому честное сравнение — не «наш 16× против их 16× на одном и том же кэше», а «мы
  *упраздняем само хранение* состояния, они его сжимают». Заявлять превосходство над
  KVQuant в байтах/ток некорректно (разные точки отсчёта: у них кэш есть, у нас — нет);
  наш вклад — в *elimination of storage*, а не в *compression of an existing cache*.
  **(По совету коллеги эту фразу — «не сжимаем кэш, а упраздняем хранение через
  детерминированный key→state map» — выносим прямо в Abstract статьи; она готова к этому.)**
- **Оригинальность здесь в двух вещах:** (1) доказательство `h = G(e)` для селективной
  PC-модели и вывод «состояние хранить не нужно вообще»; (2) генеративный unfold собственной
  хаотической картой вместо внешнего кодека.
- **Метрика шумная.** Точный PPL: 179 на 16 окнах W=65 536, 460 на 64 окнах — разброс по
  корпусу огромный. Сравнивать можно **только парные дельты на одних окнах**.
- **`gen` чувствителен к качеству кодбука** (см. 4.1) — это надо явно указать.
- **Немонотонность по степени сжатия ОБЪЯСНЕНА** (см. 4.3): смесь √(S) ADC-шума (лечится
  rerank на мелких подвекторах) и недообученного кодбука на глубоком RQ (лечится калибровкой
  ∝ числу центроидов). Opt-точка: L=2, S=12, dim=16. Свип K (64/128/512 при L=2,S=12) уже
  в `sweep_codebook.json`: 64 → −36.7 %, 128 → −13.4 %, 256 → −31.4 %, 512 → −29.0 % —
  оптимум K около 256, перебор K вредит (кластеров много, калибровки мало).
- **Улучшение PPL при сжатии на длинных окнах — ЭТО ШУМ, не результат.** Проверено
  доверительными интервалами (раздел 3.1): на W = 65 536 все дельты, включая «−15 %»,
  лежат внутри интервала, пересекающего ноль; на W = 262 144 вторая точка меняет знак
  (seed0 −33 % → seed1 +25 %). Заявлять «gen лучше exact» нельзя — заявляется «не хуже
  в пределах дисперсии при 16–32× меньшей памяти». Старый блок «рабочая точка −26.4 %»
  в разделе 4 снят.
- **Абсолютный пол памяти — это просто id токенов** (~9 бит/ток при V≈512). Коды за 24–48 Б/ток
  покупают не минимальную память, а **дешёвую селекцию** (ADC по кодам вместо точного
  косинуса по (W,d)). Это надо явно развести в тексте — см. 6.1.

### 6.1 Why not just store Token IDs? (вопрос, который 100% задаст ревьюер)

Если хранить просто id токенов (9 бит), то для селекции нужно: (1) embedding lookup,
(2) прогнать эмбеддинги через **весь `ChaoticBlock`** (перестановки, coupling), чтобы получить
ключи `e`, и только потом (3) косинус с query. Стоимость поиска **O(W·d·FLOPs_Layer)** — дорого,
это фактически повторный прогон контекста.

Если хранить Fracode-коды (24–48 Б/ток): делаем ADC **напрямую по кодам**, стоимость
**O(W·S)** чистых сложений (микросекунды, memory bandwidth). Коды покупают не минимальную
память, а **O(1)-дешёвую селекцию**: без них ни key-value кэша (его нет по конструкции),
ни быстрого поиска по окну не получить. Это и есть ответ на «зачем сжимать то, что
пересчитывается за embed-lookup».
- Модель — исследовательский прототип (d=192, 8 слоёв, BPE-TinyStories). Абсолютный PPL
  (~537) не сопоставим с SOTA; важна только парная деградация.
