## 0. Зачем (факты из профиля)

Профиль decode-шага (W=262k, d=192, L=8), `results/decode_profile.json`:

| компонент | время | доля |
|---|---|---|
| полный шаг | 256.6 мс | 100% |
| ключи e=embed+pos | 7.2 мс | 2.8% |
| пересчёт драйверов (8 слоёв, topk по W) | 72.6 мс | 28.3% |
| **прогон блоков (8 слоёв, по всему W)** | **213.9 мс** | **83.3%** |
| python-overhead | ~0 (шум) | — |

**Вывод:** 83% — прогон `blk(h, driver)` по ВСЕМУ окну W. Triton не изменит асимптотику
O(W) на шаг. Единственный рычаг, дающий порядок величины — **сократить W, на котором
работает каждый decode-шаг**, через активное окно + глубинную память.

## 1. Архитектура

Два уровня памяти:

### Уровень A — Active Window (точный, FP16)
- Последние `N_local` токенов (кандидат: 4096 или 8192).
- Хранятся ТОЧНЫЕ ключи `e = embed(x) + pos` (FP16, `(N_local, d)`), при желании —
  промежуточные состояния `h` (как классический KV-кэш).
- Драйвер строится из НИХ: `topk` по `N_local` вместо `W` → O(N_local) на шаг.
- Readout/декодинг внутри окна: O(1) по времени (все N_local уже посчитаны).

### Уровень B — Deep Memory (Fracode, 24 Б/ток)
- Всё, что за пределами активного окна (глубина на 1M+).
- Сжато иерархическим RQ (L=2, S=12, K=256) = 32×.
- ADC-поиск по кодам (O(W·S) сложений), unfold только отобранных кандидатов.
- **НЕ на каждом шаге** — асинхронно / раз в K шагов / при неуверенности.

### Механика генерации
1. `q` из последних `nquery` токенов.
2. Локальный `topk` по активному окну → быстрый драйвер.
3. **Когда** подключать глобальный поиск:
   - (a) каждые K шагов (напр. 32) — обновить драйвер из глубины;
   - (b) когда локальный topk даёт «плохой» матч (низкий косинус / высокая энтропия весов);
   - (c) асинхронно на отдельном CUDA-стриме (prefetch).
4. Драйвер = смесь локального и глобального (или замена по триггеру).

## 2. ГЛАВНАЯ ТОНКОСТЬ: readout зависит от `g = h.mean(dim=1)`

Строка 176 в `models_pc.PurePCLM.forward` (sts_prog):
```python
h_last = h[:, -1, :]
g = h.mean(dim=1)                       # СРЕДНЕЕ ПО ВСЕМУ ОКНУ
logits = self.readout3(torch.cat([h_last, q0, g], dim=-1))
```
- `g` — усреднение состояний по **всему** W. При добавлении токена меняется весь драйвер →
  все h → `g` по всему окну.
- Проблема: `g` — «глобальный контекстный сигнал», который Two-Tier должен воспроизводить
  из активного окна + глубины, иначе readout рассинхронизируется с обучением.

**Варианты решения (нужен выбор):**
1. **`g` только по активному окну** — `g = h[-N_local:].mean(0)`. Просто, но модель
   «забудет» дальний контекст в readout (сам контекст ещё влияет через драйверы).
2. **`g` = композиция:** активное окно (быстро) + один «глубинный» вектор (усреднённый
   развёрнутый драйвер из Deep Memory, пересчитываемый раз в K шагов). Сохраняет
   глобальность при O(N_local + D) вместо O(W).
3. **Заморозить `h` старого контекста** (не пересчитывать на каждом шаге, обновлять
   фоном) — но это меняет динамику (старый h не видит новый токен). Отложить.

**Рекомендация: вариант 2** — гибрид активного окна и периодического глубинного сигнала.
Он сохраняет глобальный контекст в readout, асимптотику O(N_local) на шаг, и красиво
ложится в статью как «Hierarchical Generative Memory» (кратковременная + долговременная
память). Требует эмпирической проверки: не деградирует ли PPL/конфликт-проба.

## 3. Тонкость 2: селекция использует СЫРЫЕ ключи `e`, а не `h`

`sim = (en * qn).sum(-1)` — косинус по **статичным ключам** `e` (строка 159), драйвер =
взвешенная сумма `e[nxt]`. Активное окно хранит точные `e` (FP16) → селекция по нему
идентична. Глубина хранит коды → unfold `e` для кандидатов. **Это совместимо**, но надо
проверить: FP16 активного окна против FP32 — не даст ли сдвиг топ-k (см. §5, проверка).

---

## 4. Тонкость 3: `q` зависит от последней позиции h каждого слоя

`q = q0 + query_proj(h[:, -1, :]) * 0.5` (строка 173). `h[-1]` — последняя позиция активного
окна. При декодинге она меняется каждый шаг → q меняется → пересчёт драйверов. Это
**неизбежно** в текущей механике (коллега прав), но активное окно делает этот пересчёт
дешёвым: topk по N_local вместо W.

## 5. План реализации + проверка качества

### Фаза 0 (без GPU, дизайн — СДЕЛАНО этим документом)
### Фаза 1 — прототип Two-Tier decode (GPU, ~1-2 ч)
1. Реализовать `two_tier_generate`: активное окно (FP16 e) + Fracode-глубина + readout по
   варианту 2 (активное окно + периодический глубинный g).
2. Бенчмарк скорости: tok/s на W=262k (цель ≥ 40).
3. Сравнить качество на НЕ-обучающих задачах: PPL на тех же окнах, конфликт-проба
   (logit_gap), спектр E1 — **до/после** Two-Tier.

### Фаза 2 — верификация (GPU, ~1-2 ч)
4. PPL: exact (full-W) vs two-tier (активное окно + глубинная память) на W=262k и 1M.
5. Конфликт-проба: gap не должен упасть катастрофически (глубокая память должна дотягивать
   дальние факты).
6. Триггеры глобального поиска: сравнить (a) каждые K, (b) по энтропии, (c) асинхронно.

### Фаза 3 — в статью
- «Hierarchical Generative Memory»: активное окно + глубинная Fracode-память.
- Таблица скорость × качество (two-tier vs exact vs full-W gen).
- Честные ограничения: активное окно задаёт «локальную» границу; глубина — ассоциативный
  вызов по запросу.

## 6. Вопросы к обсуждению (перед кодом)

1. **N_local** — 4096 или 8192? (8192 — точнее readout, 4096 — быстрее; проверить оба).
2. **Вариант `g`** — гибрид (вариант 2) или только активное окно (вариант 1)?
   Рекомендую 2, но это меняет readout → проверить, что `readout3` не требует переобучения
   (возможно, потребуется: `g` изменился с O(W) на O(N_local + D)).
3. **Триггер глобального поиска** — (a) каждые K, (b) энтропия, (c) асинхронно.
4. **FP16 активного окна** — достаточно ли (сдвиг top-k)?
5. **Нужно ли переобучение** readout из-за смены `g`? Если да — это отдельный шаг.
