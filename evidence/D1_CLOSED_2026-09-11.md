# D1 CLOSED — ключ `external_keys` был вырожденным

Дата: 2026-09-11. Статус: **закрыт**, обе копии исправлены и побитово совпадают.

## Что было

В `external_keys` (синтетический адресный ключ для экспериментов по переносу)
индексация подпространства PQ была написана так:

```python
idx = (h % sub).astype(np.int64)
col = (idx % sub).astype(np.int64)      # <-- ошибка: col == idx
out[rows, col * sub + idx] += sgn
```

Так как `idx < sub`, `idx % sub == idx`, значит `col == idx`. Ненулевыми
оказывались только координаты с номерами `idx*sub + idx`, то есть при
`d = 192`, `nsub = 12`, `sub = 16` — **ровно 16 из 192 координат**. Остальные
11 из 12 кодобуков L0 и L1 квантовали точные нули: **22 из 24 байт кода были
мусором**.

## Воспроизведение (до правки)

`_d1_repro.py`, минимальный числовой скрипт без обращений к архиву:

| nsub | ненулевых координат (было) | (стало) |
|---|---|---|
| 12 | **16 / 192** | 192 / 192 |
| 6 | 16 / 192 | 192 / 192 |
| 4 | 16 / 192 | 192 / 192 |
| 3 | 16 / 192 | 192 / 192 |
| 1 | 192 / 192 | 192 / 192 |

Заметь: при `nsub = 1` баг не проявлялся — поэтому его и не поймали раньше.
Все прогоны со `--nsub 1` были корректны; вырожденными оказались именно
прогоны с `--nsub 12`, который стоял дефолтом.

## Исправление

```python
col = (h % nsub).astype(np.int64)                  # номер подпространства
idx = ((h // nsub) % sub).astype(np.int64)         # координата внутри
sgn = np.where((h // (nsub * sub)) % 2 == 0, 1.0, -1.0).astype(np.float32) * wgt
np.add.at(out, (rows, col * sub + idx), sgn)
```

Исправлено в двух местах, которые обязаны быть идентичными:

* `exp_transferable_memory.py` (`external_keys`)
* `exp_transfer_crossarch.py` (побитовая копия)

Проверка идентичности: `np.array_equal(m1, m2) → True`.

Дефолт `--nsub` в `exp_transfer_crossarch.py` и `_e2e_ext_keys_strat.py`
изменён `12 → 1` с пояснением в `--help`.

## Влияние на результат

Ряд «деградация recall@8 с ростом N» существовал **только из-за бага**.

| N | старый (вырожденный) ключ | исправленный ключ |
|---|---|---|
| 4 096 | 0.828 | **1.000** |
| 8 192 | — | **1.000** |
| 16 384 | — | **1.000** |
| 32 768 | — | **0.984** |
| 65 536 | 0.234 | **0.984** |
| 131 072 | — | **0.969** |
| 262 144 | — | **0.969** |
| 524 288 | — | **0.969** |

При N = 65 536 выигрыш **4.21×**. На исправленном ключе деградации с ростом N
почти нет: 1.000 держится до 16k, дальше мягкий выход на 0.969.

Артефакты: `runs/scaling_recheck_nsub12.json`, `runs/scaling_recheck_large.json`.

## Предрегистрированные гипотезы — итог

* **H1** («вырожденный ключ объясняет деградацию в старом ряду») —
  **не воспроизводима по построению**: старый ряд целиком порождён багом,
  отдельного эффекта для проверки не осталось.
* **H2** («причина — ранг ключа, а не количество бит на подпространство») —
  **подтверждена**. После правки ранга recall@8 поднялся до 0.984–1.000 при
  тех же 24 Б/ключ.
* **H3** («вырожденный ключ можно использовать как есть: ненулевых
  подпространств 1 из 12, значит достаточно 2 Б/ключ») — **опровергнута**.
  Обрезка до 16 координат / S=1 даёт 0.047 / 0.109 / 0.125 / 0.047 / 0.016,
  то есть в 20–60 раз хуже. У исправленного ключа нет нулевых подвекторов,
  выбрасывать нечего.

## Что это меняет в продукте

1. Все прежние утверждения, опиравшиеся на ряд 0.828 → 0.234, сняты.
2. Рекомендуемая конфигурация — исправленный ключ, `nsub = 1` (полный ранг,
   один кодобук на уровень). 24 Б/токен работают именно так.
3. Результаты §13.6/§13.8 (стоимость внешнего адресного пространства),
   полученные на вырожденном ключе, **подлежат переизмерению**.
